================================================================================
                                THE KRU CODEX
        The Official Specification of the Kru Programming Language
================================================================================

Version 0.1 Alpha (Revised 4) — Status: Living Specification

    "A programming language should not force the programmer to think like
    the compiler. The compiler should understand the programmer."

Where ambiguity exists, this Codex takes precedence over any compiler
implementation. The compiler follows the language; the language does not
follow the compiler.

VOLUME I — FOUNDATIONS
================================================================================

--------------------------------------------------------------------------------
Chapter 1 — Preface & Mission
--------------------------------------------------------------------------------

Kru was not created because existing programming languages were incapable.
It was created because they became unnecessarily complicated.

For decades, systems programming has been synonymous with artificial
complexity: massive template systems, rigid borrow checkers, complex macros
and preprocessors, verbose boilerplate syntax, arcane compiler diagnostics,
forty years of backwards-compatibility cruft, and thousands of pages of
standards.

None of these are individually failures. Together, they create an
unnecessary barrier between the programmer and the machine. Kru exists to
remove that barrier.

    The machine is already complicated. The language should not be.

Kru has one primary goal: MAKE SYSTEMS PROGRAMMING FEEL NATURAL.

Not simplified, not abstracted away — natural. A Kru programmer should
understand exactly what the machine is doing without fighting the language
to express it. The compiler performs the heavy lifting; the programmer
focuses on solving problems.

--------------------------------------------------------------------------------
Chapter 2 — The Ten Principles
--------------------------------------------------------------------------------

  1. ZERO NOISE
     Every character communicates useful information.
         pr("Hello World")            -- good
         std::cout << "Hello World" << std::endl;   -- bad

  2. READABILITY THROUGH SIMPLICITY
     A beginner should read a Kru program within minutes; nothing occurs
     implicitly.

  3. PERFORMANCE IS A FEATURE
     Compile-time over runtime, inlining over dynamic dispatch,
     monomorphization over interpretation, native over virtualized
     execution.

  4. ZERO-COST ABSTRACTIONS
     Abstractions are allowed; hidden runtime penalties are not.

  5. THE COMPILER EXISTS TO HELP
     Every diagnostic answers: what happened, why, and how to fix it.

  6. SECURITY IS THE DEFAULT
     Secure strings, compile-time literal encryption, automatic memory
     wiping, secure arenas, capability-based restrictions, deterministic
     compile-time execution.

  7. DETERMINISTIC COMPILATION
     Identical source, compiler version, and flags produce an identical
     binary. Randomness is always explicit, never accidental.

  8. FIRST-PARTY ECOSYSTEM
     Networking, filesystem, database interfaces, allocators, threading,
     and cryptography ship in the standard library.

  9. SCALE ACROSS DOMAINS
     From embedded drivers to game engines to database servers, the core
     syntax stays consistent.

 10. TWO LANGUAGES, ONE ECOSYSTEM
     Kru (systems: backend, drivers, memory, servers, databases) and Kru-X
     (frontend: desktop/native UI, application development) share one
     compiler, toolchain, package manager, and syntactic root. Neither
     replaces the other.

--------------------------------------------------------------------------------
Chapter 3 — Mental Model & Scope
--------------------------------------------------------------------------------

Variables exist somewhere. Memory exists somewhere. Pointers point
somewhere. Nothing "just happens." The programmer understands the movement
and structure of data; the compiler optimizes those movements without
obscuring them.

WHAT KRU IS NOT

  - Not a replacement for every domain.
  - Not burdened by decades of backwards-compatibility compromise.
  - Not an interpreted scripting language.
  - Not garbage-collected.
  - Not an obscure macro-heavy DSL.

THE FINAL RULE

    Every proposal to Kru must answer:
    "Does this make writing efficient systems software simpler without
    hiding how the machine works?"

    Yes -> it belongs in Kru.
    No  -> it does not.

--------------------------------------------------------------------------------
Chapter 4 — Source Files
--------------------------------------------------------------------------------

The Kru ecosystem uses three source formats:

    Extension    Purpose
    ---------    ------------------------------------------
    .kru         Native Kru source
    .krux        Kru-X application source
    .kh          Kru header / interface definition

A source file contains declarations, definitions, imports, attributes,
and compile-time instructions. No mandatory module declaration is
required — the filename determines the compilation unit.

    pub fn main() -> i32 {
        pr("Hello, World!")
        ret 0
    }

--------------------------------------------------------------------------------
Chapter 5 — Lexical Structure
--------------------------------------------------------------------------------

ENCODING
    UTF-8. ASCII identifiers are required in 0.1; Unicode string literals
    and comments are accepted. Unicode identifiers are implementation-
    defined for now.

WHITESPACE
    Separates tokens only; does not affect meaning. Official formatting
    requires indentation, but the parser does not.

COMMENTS
    // single-line

    /*
        block comment
    */

    /// documentation comment (attaches to the next declaration)

STRING LITERALS
    Double-quoted, UTF-8 encoded. The following escape sequences are
    recognized inside string and character literals:

        \n     newline (U+000A)
        \r     carriage return (U+000D)
        \t     horizontal tab (U+0009)
        \\     backslash
        \"     double quote
        \'     single quote
        \0     null byte (U+0000)
        \xHH   byte with hex value HH (e.g. \x41)
        \u{X}  Unicode scalar value (e.g. \u{0041})

    Raw strings are prefixed with r and do not process escapes:

        r"C:\Users\data"        -- literal backslashes, no escapes

NUMERIC LITERALS
    Integer literals may be decimal, hexadecimal, binary, or octal:

        123        decimal
        0xFF       hexadecimal
        0b1010     binary
        0o777      octal

    Underscores may be used as visual separators in integer literals:

        1_000_000
        0xFF_FF_FF

    Integer literals may carry an explicit type suffix to override
    default inference:

        42u8       100i64      0xFFu16

    Without a suffix, integer literals default to i32. If the value
    exceeds i32 range, the compiler promotes to i64, then i128, then
    reports an overflow error.

    Float literals:

        3.14       1.0        2.5e10       1.0e-3

    Float literals default to f64. A suffix may be used:

        3.14f32

CHARACTER LITERALS
    Single-quoted, representing a single Unicode scalar value:

        'A'        'π'        '\n'        '\u{1F600}'

BOOLEAN LITERALS
    true   false

Chapter 6 — Keywords
--------------------------------------------------------------------------------

The following words are reserved and cannot be used as identifiers:

    fn   pub   ret   let   var   ref   const
    if   else  match while loop  break continue
    struct enum type  trait impl  Self self
    arena unsafe secure comptime inline
    use  extern cast  test
    for  in

RESERVED FOR FUTURE USE (not yet functional in 0.1 Alpha):

    async  await  actor  interface  where
    yield  defer  operator  macro

BUILT-IN IDENTIFIERS (not reserved, but predefined by the language
or standard library; shadowing them is legal but discouraged):

    true   false   null   pr   panic   assert   assert_equal
    assert_error   Ok   Err   Some   None   Result   Option   Copy

Note: `null` is valid only where a raw pointer type (`*T`) is
expected, and only inside `unsafe` (Chapter 26, "Raw Pointers").
`Option<T>` is the general-purpose "no value" type everywhere else;
`null` does not participate in `match` and does not generalize
beyond `*T`.

Note: `self` is a contextual keyword — it is reserved only as the
first parameter name of a method; it may be used as a variable name
in non-method contexts. `Self` is a contextual keyword inside trait
and impl bodies.

Note: `mod` is NOT a keyword — modules are determined by filename
(Chapter 87). This avoids a redundant declaration that could
conflict with the filename-based module system.

Note: `extern` is used for FFI function declarations (Appendix C).
`for` and `in` are used together for iteration (Chapter 19).

KRU-X KEYWORDS (valid only in .krux files):

    component

    `component` is a contextual keyword reserved for Kru-X source
    files (.krux). It marks a struct as a UI component with implicit
    arena scoping (Chapter 70). In plain Kru (.kru) files, `component`
    is a regular identifier and may be used freely.

--------------------------------------------------------------------------------
Chapter 7 — Identifiers & Naming
--------------------------------------------------------------------------------

Identifiers begin with a letter or underscore, then contain letters,
digits, or underscores. Keywords are reserved.

    Kind          Style             Example
    ----          -----             -------
    Variables     snake_case        packet_size
    Functions     snake_case        calculate_checksum()
    Types         PascalCase        NetworkPacket
    Traits        PascalCase        Serializable
    Enum variants PascalCase        ConnectionState
    Constants     SCREAMING_CASE    MAX_CONNECTIONS
    Modules       snake_case        network::http
    Generic params single uppercase T, K, V, E

Long descriptive names are preferred over abbreviations.

    Preferred:    connection_timeout
    Avoid:        conn_timeout

Exceptions exist for universally understood technical terms: id, ip,
url, cpu, gpu, ram, mac, ttl, dns, ssl.

--------------------------------------------------------------------------------
Chapter 8 — Variables & Bindings
--------------------------------------------------------------------------------

Kru has two binding forms. IMMUTABLE IS THE DEFAULT.

    let age := 25          // immutable, inferred i32
    age = 30               // error: immutable binding cannot be modified

    var counter := 0       // mutable
    counter = counter + 1  // OK

BOTH let AND var USE := FOR INITIALIZATION. The = operator is used
only for assignment to an existing mutable binding. This is a deliberate
choice: := means "create and initialize," = means "assign to existing."

EXPLICIT TYPING
    let port: u16 := 8080
    var buffer: [u8; 1024] := [0; 1024]

The compiler verifies that 8080 fits in u16.

SHADOWING is permitted — a new let/var with the same name replaces it
for the rest of the current scope; the original binding remains valid
for anything that already captured it.

    let name := "Alice"
    let name := name.len()    // shadows; name is now u32

DECLARATION WITHOUT INITIALIZATION
    A var binding may be declared without an initializer, but reading
    it before assignment is a compile error:

    var config: Config       // declared, uninitialized
    config = load_config()   // now initialized
    pr(config)               // OK

    let bindings MUST be initialized at declaration — an uninitialized
    immutable binding has no value to be immutable.

Design rationale: Kru assumes most data should not change. Mutation is
powerful, and power requires visibility — hence the explicit `var`.

Chapter 9 — Primitive Types
--------------------------------------------------------------------------------

    i8  i16  i32  i64  i128        signed integers
    u8  u16  u32  u64  u128        unsigned integers
    f32 f64                        floating point (IEEE 754)
    bool                           true / false
    char                           Unicode scalar value (4 bytes)
    str                            UTF-8 string slice (see Chapter 20)

INTEGER RANGES

    Type   Minimum              Maximum
    ----   -------              -------
    i8     -128                 127
    u8     0                    255
    i16    -32768               32767
    u16    0                    65535
    i32    -2147483648          2147483647
    u32    0                    4294967295
    i64    -2^63                2^63 - 1
    u64    0                    2^64 - 1
    i128   -2^127               2^127 - 1
    u128   0                    2^128 - 1

The target platform determines the size of `isize` and `usize` — these
are pointer-sized signed and unsigned integers respectively. On a 64-bit
target they are equivalent to i64/u64; on a 32-bit target, i32/u32.

BOOL
    A bool is one byte. true is 1, false is 0. Booleans do not
    implicitly convert to or from integers.

CHAR
    A char is a 4-byte Unicode scalar value. It is distinct from u32;
    explicit conversion is required between them.

TYPE SIZES AND ALIGNMENT
    All primitive type sizes are fixed across targets for a given bit
    width (32-bit vs 64-bit). The alignment of each primitive equals
    its size, except for i128/u128 which are 16-byte aligned on most
    targets.

Chapter 10 — References, Pointers, and the @ Operator
--------------------------------------------------------------------------------

Kru distinguishes between values, references, and raw pointers. This
distinction is made visible in the source text — nothing is implicit.

REFERENCES
    A reference is a non-owning handle to a value. References are
    created with the `ref` keyword:

    let value := 42
    let r := ref value          // immutable reference to value
    let mr := mut ref value     // mutable reference to value

    - `ref x` creates an immutable reference (read-only access)
    - `mut ref x` creates a mutable reference (read-write access)
    - Multiple immutable references may coexist
    - A mutable reference must be the ONLY live reference (Chapter 25)

    A reference's type is written as `ref T` or `mut ref T`:

    fn read_value(r: ref i32) -> i32
    fn write_value(r: mut ref i32, new_value: i32)

THE @ OPERATOR (DEREFERENCE / LOAD)
    @ is postfix and means "read the value through this reference."

    let value := pointer@                     // load through reference
    let offset := region.offset(0x40)@       // call offset(), then read
                                               // through the returned ref

    Where other languages write *value or hide the load entirely, Kru
    writes value@ — the memory boundary is visible at the call site.
    A bare `pointer` denotes the reference itself; `pointer@` denotes
    the value it refers to.

    RULE: you cannot accidentally read through a reference in Kru — @
    must appear explicitly.

    PRECEDENCE WITH METHOD CALLS: @ binds at the highest precedence
    (level 1, Chapter 11). This means `obj@.method()` parses as
    `(obj@).method()` — the value is loaded first, then the method is
    called on the loaded value. To call a method through a reference
    without loading the value first, use `ref self` or `mut ref self`
    as the method receiver (Chapter 16) and call `obj.method()`
    directly — the compiler passes the reference, not the loaded value.

    Summary:
        ptr@              load value through reference
        ptr@.field        load value, then access field
        ptr.method()      call method through reference (no load)
        ptr@.method()      load value, then call on loaded value

    Use `ptr@.method()` when the method takes `self` by value.
    Use `ptr.method()` when the method takes `ref self` or
    `mut ref self`.

WRITING THROUGH A MUTABLE REFERENCE
    Assignment through a mutable reference uses `@ =`:

    var counter := 0
    let mr := mut ref counter
    mr@ = 10           // writes 10 to counter through mr
    pr(mr@)            // prints 10

RAW POINTERS
    Raw pointers are unmanaged addresses, created and used only inside
    `unsafe` blocks. Their type is `*T` (pointer to T):

    unsafe {
        let addr: *u8 := 0x1000    // raw address
        let byte := addr@          // read through raw pointer
    }

    Raw pointers are exempt from the aliasing and lifetime rules of
    Chapters 24-26. They exist for FFI, kernel code, and direct memory
    manipulation. They must never appear outside `unsafe`.

OWNERSHIP OF REFERENCES
    A reference never owns the memory it points to. The original binding
    (let/var) owns the value; the reference borrows it. References are
    stack-allocated and follow the scope rules of Chapter 24.

FULL aliasing, validity, and lifetime rules for @ are specified in
Volume III — Memory, since they depend on the arena/ownership model.

Chapter 11 — Expressions & Operators
--------------------------------------------------------------------------------

    Arithmetic:       +  -  *  /  %
    Bitwise:          &  |  ^  ~  <<  >>
    Comparison:       ==  !=  <  >  <=  >=
    Logical:          &&  ||  !
    Assignment:       =   (mutable bindings only)
    Compound assign:  +=  -=  *=  /=  %=
                     &=  |=  ^=  <<=  >>=
    Memory:           @   (postfix read)
    Reference:        ref   mut ref

COMPOUND ASSIGNMENT
    Compound assignment operators combine an arithmetic or bitwise
    operation with assignment. They are only valid on mutable bindings
    or mutable references:

    var total := 0
    total += 5          // equivalent to: total = total + 5
    total <<= 2         // equivalent to: total = total << 2

BITWISE OPERATORS
    &    bitwise AND
    |    bitwise OR
    ^    bitwise XOR
    ~    bitwise NOT (unary prefix)
    <<   left shift
    >>   right shift (arithmetic for signed, logical for unsigned)

    Bitwise operators are defined for all integer types. They are not
    defined for bool — use && and || for logical operations.

PRECEDENCE (highest to lowest):

    Level  Operators                          Associativity
    -----  ---------                          -------------
      1    @ (postfix), call(), field . []   left
      2    unary !, unary -, unary ~          right
      3    *  /  %                            left
      4    +  -                               left
      5    <<  >>                             left
      6    &                                  left
      7    ^                                  left
      8    |                                  left
      9    <  >  <=  >=                       left
     10    ==  !=                             left
     11    &&                                 left
     12    ||                                 left
     13    =  +=  -=  *=  /=  %=  &=  |=  ^=  right
          <<= >>=

    Parentheses () always override precedence explicitly.

ASSOCIATIVITY NOTE
    Compound assignment and plain assignment are right-associative and
    produce no value — they cannot be chained in an expression context.
    `a = b = 5` is a compile error; each assignment is a separate
    statement.

Chapter 12 — Functions
--------------------------------------------------------------------------------

    fn name(args) -> type { }
    pub fn name(args) -> type { }

    pub fn add(a: i32, b: i32) -> i32 {
        ret a + b
    }

NO IMPLICIT RETURN — every function that produces a value must reach an
explicit `ret`. A function with no return type (no `-> type`) returns
void and does not need a `ret` statement; a bare `ret` with no value is
legal for early exit.

PARAMETER PASSING
    Parameters are passed by value by default. To pass by reference,
    use `ref T` or `mut ref T` as the parameter type:

    fn increment(r: mut ref i32) {
        r@ += 1
    }

    fn read_config(cfg: ref Config) -> u32 {
        ret cfg.port
    }

    Passing by value copies the argument. Passing by reference borrows
    it without copying. See Chapter 10 for reference semantics and
    Chapter 24 for ownership rules.

DEFAULT ARGUMENTS
    Kru does not support default arguments. Every argument must be
    provided at the call site. This keeps call sites unambiguous and
    diagnostics traceable (Principle V).

OVERLOADING
    Kru does not support ad-hoc overloading by argument type — this
    would reintroduce hidden dispatch resolution, violating Principle
    IV (Zero-Cost Abstractions) and Principle V (diagnostics must be
    traceable to one definition). Instead, differently-shaped operations
    get differently-named functions (parse_i32, parse_f64), or are
    expressed through generics (Chapter 21) resolved entirely at compile
    time via monomorphization — so "overload resolution" never happens
    at runtime, and a diagnostic always points at exactly one concrete
    instantiation.

INLINING
    `inline fn` is a hint the compiler is free to honor or ignore in 0.1
    Alpha; a future revision may make it a directive under `comptime`
    guarantees (Volume V).

Chapter 13 — Closures
--------------------------------------------------------------------------------

Closures are anonymous functions that capture bindings from their
enclosing scope. Captures are EXPLICIT — the programmer lists what the
closure captures and how:

    let threshold := 10

    let over_threshold := fn(x: i32) -> bool [threshold] {
        ret x > threshold
    }

CAPTURE LIST SYNTAX
    The capture list appears in square brackets after the parameter
    list:

    [name]           capture by value (immutable copy)
    [mut name]       capture by value (mutable copy)
    [ref name]      capture by immutable reference
    [mut ref name]  capture by mutable reference

    Multiple captures are comma-separated:

    let handler := fn(event: Event) -> bool [ref config, mut ref state] {
        ...
    }

A closure's capture list is part of its type — two closures with
different captures are different types, even with identical signatures.
This keeps closures zero-cost: no hidden heap allocation for a capture
environment unless the closure escapes its defining scope.

ESCAPING CLOSURES
    A closure "escapes" when it is stored in a location that outlives
    the scope where the closure was defined — for example, returned
    from a function, stored in a struct field, or passed to a spawn.

    When a closure captures by value (`[name]` or `[mut name]`), the
    captured values are copied/moved into the closure's storage. This
    is always safe — the closure owns its own copy, so it may escape
    freely without any annotation:

    fn make_multiplier(factor: i32) -> fn(i32) -> i32 {
        ret fn(x: i32) -> i32 [factor] {
            ret x * factor    // factor is a copy, safe to escape
        }
    }

    When a closure captures by REFERENCE (`[ref name]` or
    `[mut ref name]`), the closure holds a reference to the captured
    binding. If the closure escapes the scope of that binding, the
    reference would dangle — this is a compile error (K3003: escaping
    closure captures reference to local binding).

    To make a reference-capturing closure escape, the programmer must
    either:
      1. Change the capture to by-value (`[name]` instead of `[ref name]`)
      2. Move the captured binding into an outer scope or arena so the
         reference remains valid
      3. Use a heap allocation for the captured data

    This is consistent with Volume III's scope-bound reference rule
    (Chapter 24): a reference cannot outlive its region, and a closure
    that captures by reference is bound by the same rule as any other
    reference.

CLOSURES WITHOUT CAPTURES
    A closure with an empty capture list `[]` is a plain function
    pointer and can be stored in a `fn` typed variable:

    let double: fn(i32) -> i32 := fn(x: i32) -> i32 [] {
        ret x * 2
    }

--------------------------------------------------------------------------------
Chapter 14 — Control Flow
--------------------------------------------------------------------------------

IF / ELSE

    if x > 5 {
        pr("big")
    } else if x > 0 {
        pr("small")
    } else {
        pr("negative")
    }

WHILE LOOP

    while condition {
        do_work()
    }

    The condition is checked before each iteration. If the condition is
    false on entry, the body never executes.

LOOP (infinite loop)

    loop {
        if done { break }
        continue
    }

BREAK AND CONTINUE
    `break` exits the innermost loop. `continue` skips to the next
    iteration of the innermost loop. Both work in `while` and `loop`.

    Loop labels are supported for nested loops:

    outer: loop {
        inner: loop {
            if found { break outer }
        }
    }

EXPRESSION BLOCKS
    A block `{ ... }` is an expression whose value is the value of its
    LAST expression. This allows inline computation without a named
    function:

    let area := {
        let w := 10
        let h := 20
        w * h          // no `ret` — last expression is the block's value
    }

    The last expression in a block is its value. Statements like
    `let`, `var`, and assignments produce no value — they must not be
    the last item in a block used as an expression. A block ending in
    a statement is a void block (value is void).

    To return from the ENCLOSING FUNCTION from inside a block
    expression, use `ret` as normal — `ret` always returns from the
    nearest enclosing FUNCTION, never from a block. This is the key
    distinction from the last-expression rule:

        fn calculate(x: i32) -> i32 {
            let clamped := {
                if x > 100 { ret 100 }    // returns from calculate()
                if x < 0 { ret 0 }        // returns from calculate()
                x                          // block's value if no early ret
            }
            ret clamped * 2
        }

    RULE: `ret` always returns from a function. A block's value is
    its last expression (which must not be a `ret` statement). This
    eliminates the ambiguity of overloading `ret` for two purposes.

    A block used as a statement (not as an expression value) may end
    in any statement — its value is discarded.

Chapter 15 — Pattern Matching & match
--------------------------------------------------------------------------------

`match` is exhaustive — the compiler rejects a match that does not
cover every variant unless a `_` catch-all arm is present:

    match opcode {
        Opcode.Load  => { ret value }
        Opcode.Store => { ret Ok(()) }
        _            => { ret Err(Error.InvalidOpcode) }
    }

PATTERN FORMS

    1. LITERAL PATTERNS match a specific value:

        match status_code {
            200 => { pr("OK") }
            404 => { pr("Not Found") }
            _   => { pr("Other") }
        }

    2. ENUM VARIANT patterns match by variant name:

        match connection {
            ConnectionState.Connected    => { }
            ConnectionState.Disconnected => { }
        }

    3. ENUM VARIANT WITH PAYLOAD binds the payload:

        match token {
            TokenType.AssignImmut          => { }
            TokenType.Number(value)        => { pr(value) }
            _                              => { }
        }

    4. STRUCT DESTRUCTURING binds fields by name:

        match point {
            Point { x, y } => { pr(x + y) }
        }

    5. WILDCARD `_` matches anything and binds nothing.

    6. BINDING `name @` binds the matched value to a name. Combined
       with a match guard (above), this enables conditional destructuring:

        match config {
            c @ Config { timeout, .. } if timeout > 0 => {
                pr(timeout)
            }
            _ => { }
        }

MATCH GUARDS
    A match arm may include a guard — an `if` condition that must
    also be true for the arm to match:

        match config {
            Config { timeout, .. } if timeout > 0 => {
                pr(fmt("timeout is {0}", timeout))
            }
            Config { timeout, .. } if timeout == 0 => {
                pr("no timeout")
            }
            _ => { pr("default") }
        }

    Guards are evaluated AFTER the pattern matches. If a guard fails,
    the compiler tries the next arm — the match is not exhaustive
    at the guard level, only at the pattern level. This means a
    guard that always fails does not cause a compile error, but the
    compiler warns (K2003: match arm with always-false guard) when
    it can prove the guard is constant-false.

    Guards may reference bindings from the pattern:

        match packet {
            Packet { port, .. } if port == 80 || port == 443 => {
                ret classify_http(packet)
            }
            Packet { port, .. } if port < 1024 => {
                ret classify_privileged(packet)
            }
            _ => { ret classify_other(packet) }
        }

    Guards must be pure expressions (no side effects, no I/O). The
    compiler enforces this at the semantic analysis stage (Chapter
    44) — a guard that calls a function with side effects is a
    compile error (K1006: impure expression in match guard).

EXHAUSTIVENESS
    The compiler verifies exhaustiveness at compile time. A match on an
    enum must cover every variant or include a `_` catch-all. A match
    on a struct must either destructure all fields or use `..` to
    ignore remaining fields. A match on a primitive requires a `_` arm
    unless every possible value is covered (practical only for bool).

--------------------------------------------------------------------------------
Chapter 16 — Structs
--------------------------------------------------------------------------------

    struct Person {
        name: str
        age: i32
    }

    let p := Person {
        name: "Bob",
        age: 20
    }

    p.age       // field access

METHODS
    Methods are declared in `impl` blocks (Chapter 33). Methods take an
    EXPLICIT `self` parameter as their first parameter — there is no
    implicit receiver:

    impl Person {
        fn is_adult(self) -> bool {
            ret self.age > 18
        }
    }

    The `self` parameter may be a value, an immutable reference, or a
    mutable reference:

    impl Person {
        fn age(self) -> i32 {              // takes Person by value
            ret self.age
        }

        fn display(ref self) -> str {       // takes ref Person
            ret self.name
        }

        fn birthday(mut ref self) {         // takes mut ref Person
            self.age += 1
        }
    }

    Methods are called with dot syntax: p.is_adult()

TUPLE STRUCTS
    A tuple struct has unnamed fields, accessed by index:

    struct Color(u8, u8, u8)

    let red := Color(255, 0, 0)
    pr(red.0)    // 255

UNIT STRUCTS
    A struct with no fields, used as a marker type:

    struct Unit

DEFAULT FIELD VALUES
    Struct fields may specify default values, used when a field is
    omitted from initialization:

    struct ServerConfig {
        port: u16 := 8080
        host: str := "0.0.0.0"
        max_connections: u32 := 100
    }

    let cfg := ServerConfig { port: 3000 }
    // host defaults to "0.0.0.0", max_connections defaults to 100

--------------------------------------------------------------------------------
Chapter 17 — Enums
--------------------------------------------------------------------------------

Enums may carry payloads per-variant, in the style of Result<T, E>
and Opcode:

    enum Opcode {
        Load
        Store
        Jump(addr: u64)
        Call(target: u64, args: u32)
    }

Enum variants are constructed by name:

    let op := Opcode.Jump(0x1000)
    let st := Opcode.Store

Enum variants with payloads can be destructured in match (Chapter 15):

    match op {
        Opcode.Jump(addr) => { pr(addr) }
        Opcode.Call(target, args) => { pr(target) }
        _ => { }
    }

ENUMS WITH EXPLICIT DISCRIMINANTS
    Payload-free variants may have explicit integer discriminants:

    enum HttpStatus: u16 {
        Ok = 200
        NotFound = 404
        InternalError = 500
    }

    The underlying integer value can be accessed with `cast`:

    let code: u16 := cast<u16>(HttpStatus.Ok)

--------------------------------------------------------------------------------
Chapter 18 — Result, Option, and Error Handling
--------------------------------------------------------------------------------

Kru does not use exceptions. Error handling is explicit through two
standard library enum types.

OPTION<T>
    Represents a value that may not exist:

    enum Option<T> {
        Some(value: T)
        None
    }

    fn find_user(id: u64) -> Option<User>

    Option should be used when absence is expected behavior, not an
    error condition.

RESULT<T, E>
    Represents success or failure:

    enum Result<T, E> {
        Ok(value: T)
        Err(error: E)
    }

    fn open(path: str) -> Result<File, Error>

    A function returning Result must explicitly handle both outcomes.
    The compiler enforces this through match exhaustiveness (Chapter 15).

CONSTRUCTORS
    Ok(value) and Err(error) construct Result values.
    Some(value) and None construct Option values.
    These are enum variant constructors, not special syntax.

THE ? OPERATOR (ERROR PROPAGATION)
    The `?` suffix on an expression that returns Result or Option
    short-circuits on the error/none case:

    fn read_config(path: str) -> Result<Config, Error> {
        let file := kru::fs::open(path)?    // propagates Err
        let text := file.read_to_string()?  // propagates Err
        ret parse_config(text)
    }

    `expr?` is sugar for:

    match expr {
        Ok(v) => v
        Err(e) => { ret Err(e) }
    }

    For Option:

    match expr {
        Some(v) => v
        None => { ret None }
    }

    The `?` operator requires the enclosing function to return a
    compatible Result or Option type.

PANIC
    `panic()` is a built-in for unrecoverable failures:

    panic("invariant violated: buffer is null")

    Panic is intended for:
      - impossible states
      - violated internal assumptions
      - corrupted program invariants

    It is not intended as normal error handling. Panic terminates the
    process immediately — there is no catch, no unwind, no recovery.

ERROR TYPE
    The standard library provides a base Error type and an Error trait
(Chapter 32). Custom error types implement the Error trait and can be
    used as the E parameter of Result<T, E>.

--------------------------------------------------------------------------------
Chapter 19 — Arrays, Slices, and Indexing
--------------------------------------------------------------------------------

FIXED ARRAYS
    A fixed-size array has a compile-time-known length:

    let buffer: [u8; 256] := [0; 256]
    let primes := [2, 3, 5, 7, 11]

    Array type syntax: [T; N] where N is a comptime-known usize.
    Array literal syntax: [value; count] for fill, [a, b, c] for
    explicit element listing.

    Array indexing uses square brackets:

    let first := primes[0]
    primes[4] = 13        // if primes is mutable

    Array access is bounds-checked by default (Chapter 26). The check
    can be disabled inside `unsafe` for hot loops.

SLICES
    A slice is a reference to a contiguous subsequence of an array or
    other contiguous storage. Its type is `ref [T]`:

    let data: [i32; 5] := [1, 2, 3, 4, 5]
    let view: ref [i32] := data[1..4]     // elements at index 1, 2, 3

    Slice range syntax:
        arr[a..b]     elements from index a to b (exclusive)
        arr[a..]      elements from index a to end
        arr[..b]      elements from start to b (exclusive)
        arr[..]       all elements

    WHOLE-ARRAY DECAY
        `ref arr` on a whole `[T; N]` (no range) also produces a
        `ref [T]` slice spanning all N elements — it is exactly
        `arr[..]` with the range elided, not a distinct `ref [T; N]`
        array-reference type. Kru does not have a separate
        "reference to a fixed-size array" type; every array reference
        is a slice, whether or not a range narrowed it:

        let arr: [i32; 4] := [10, 20, 30, 40]
        let rs: ref [i32] := ref arr          // same as ref arr[..]
        pr(rs.len())                          // 4

    A slice carries a pointer and a length. The length is checked at
    access time (same bounds-checking rules as arrays).

ARRAY ITERATION
    Kru provides a `for` loop for iterating over arrays, slices, and
    any type implementing the Iterable trait:

    FOR LOOP

    for item in collection {
        process(item)
    }

    The `for` loop iterates over each element of the collection.
    The loop variable (`item`) is immutable by default and is a
    copy of each element (for Copy types) or a move (for non-Copy
    types). To iterate by reference, use `ref` or `mut ref`:

    for ref item in data {
        pr(item@)           // read through reference
    }

    for mut ref item in data {
        item@ += 1          // modify in place
    }

    ITERATING BY INDEX
    To iterate with an index, use a range:

    for i in 0..data.len() {
        pr(fmt("{0}: {1}", i, data[i]))
    }

    Range syntax (same as slice ranges, Chapter 19 Slices):
        a..b     indices from a to b (exclusive)
        a..      indices from a to end
        ..b      indices from 0 to b (exclusive)
        ..       all indices

    BREAK AND CONTINUE
    `break` and `continue` work in `for` loops exactly as in `while`
    and `loop` (Chapter 14). Labeled break/continue is supported:

    outer: for row in matrix {
        inner: for cell in row {
            if cell == target { break outer }
        }
    }

    ITERABLE TRAIT
    The `for` loop desugars to a call to `.next()` on an iterator
    until it returns None. The Iterable trait (Chapter 32) provides
    a default iterator for arrays and slices. Custom types may
    implement Iterable to support `for` loops.

    The desugaring of:
        for x in items { body }

    is approximately:
        let iter := items.iter()
        loop {
            match iter.next() {
                Some(x) => { body }
                None => { break }
            }
        }

    This is zero-cost: no hidden allocation, no boxed iterator object.
    The iterator is stack-allocated and inlined.

--------------------------------------------------------------------------------
Chapter 20 — Strings
--------------------------------------------------------------------------------

Kru has three string types, each with distinct semantics.

str — STRING SLICE
    A UTF-8 string slice. Similar to a slice of bytes but guaranteed
    valid UTF-8. String literals have type str:

    let greeting: str := "Hello, World!"

    A str is a reference type — it borrows its data, does not own it.
    Its lifetime is tied to the scope that owns the backing storage
    (usually a string literal in the binary's data section).

String — OWNED STRING
    A heap-owned, mutable, growable UTF-8 string. Allocation is explicit
    — constructing a String involves a heap allocation:

    let mut_name := String.from("Alice")
    mut_name.push_str(" Smith")

    String does not implicitly convert to str. To get a str from a
    String, call `.as_str()`:

    let s: str := mut_name.as_str()

SecureString — SECURE STRING
    A distinct type for sensitive data (passwords, keys, tokens).
    See Chapter 62 (Volume VII) for full semantics. Key properties:
      - Memory is wiped on destruction
      - Cannot be printed (pr(secure_string) is a compile error)
      - Uses constant-time comparison
      - Does not implicitly convert to or from str

STRING CONCATENATION
    The + operator is NOT defined for strings. Use the explicit
    `concat` function or String methods:

    // Using String methods (modifies in place):
    let mut_name := String.from("Alice")
    mut_name.push_str(" Smith")
    // mut_name is now "Alice Smith"

    // Using concat (returns a new String):
    let full := concat(first, last)

    This avoids hidden allocations from operator overloading. Every
    string concatenation is visible in the source as a function call
    or method call — no `+` silently allocating.

STRING LENGTH
    `.len()` returns the byte length (not character count) for str and
    String. `.char_count()` returns the number of Unicode scalar values.

CHARACTERS
    A single `char` is a 4-byte Unicode scalar value. Characters do not
    implicitly convert to str. Use `char.to_str()` or string interpolation.

--------------------------------------------------------------------------------
Chapter 21 — Generics & Monomorphization
--------------------------------------------------------------------------------

Kru generics are resolved entirely at compile time — there is no runtime
generic representation, no vtable, no boxing.

    fn identity<T>(x: T) -> T {
        ret x
    }

Given calls identity<i32>(5) and identity<f64>(2.0), the compiler emits
two fully specialized functions — identity__i32 and identity__f64 — as if
the programmer had hand-written each. This is the same mechanism that
keeps add<T> zero-cost:

    fn add<T: Addable>(a: T, b: T) -> T {
        ret a.add(b)
    }
    // compiler generates: add__i32, add__f32, ... for every call site's
    // concrete T that implements Addable

TYPE INFERENCE FOR GENERIC CALLS
    Type arguments can be omitted when they can be inferred from the
    call context:

    let x := identity(5)       // T inferred as i32
    let y := identity<f64>(5)  // T explicitly f64, 5 cast

Constraints on T (e.g. "must support +") are specified through traits
(Volume IV, Chapter 34).

--------------------------------------------------------------------------------
Chapter 22 — Compile-Time Execution
--------------------------------------------------------------------------------

The `comptime` keyword marks a block or expression that must be fully
evaluated during compilation, never at runtime:

    const MAX_CONNECTIONS: u32 := comptime { 64 * 4 }

COMPILE-TIME FUNCTIONS
    Functions may be marked `comptime fn` to require they are only
    callable during compilation:

    comptime fn fib(n: u32) -> u32 {
        if n < 2 { ret n }
        ret fib(n - 1) + fib(n - 2)
    }

    const FIB_10: u32 := comptime { fib(10) }

CONSTANTS
    The `const` keyword declares a compile-time constant — a value
    computed once at compile time and inlined at every use site. Unlike
    `let`, a `const` has no storage location; it is a pure compile-time
    value:

    const BUFFER_SIZE: u32 := 4096
    const PI: f64 := 3.14159265358979

    A `const` must be initialized with a comptime-evaluable expression.
    A `let` may be initialized with any runtime expression.

TYPE ALIASES
    The `type` keyword creates a type alias — a new name for an
    existing type. Aliases are resolved at compile time and produce no
    runtime overhead:

    type Port := u16
    type UserId := u64
    type Callback := fn(i32) -> bool

Per Principle VII (Deterministic Compilation), comptime code cannot
observe real-world nondeterminism — no I/O, no system clock, no
uninitialized memory — unless the programmer explicitly opts into a
documented nondeterministic intrinsic. This is what makes "compile-time
literal encryption" (Principle VI) meaningful as a build-time transform
rather than a source of accidental randomness in the binary.

================================================================================
VOLUME III — MEMORY
================================================================================

This volume exists to answer the question every serious systems language
must answer precisely: what, exactly, does Kru guarantee about memory?
Everything here is written to be checkable, not aspirational — every claim
below is scoped to exactly the conditions under which it holds.

--------------------------------------------------------------------------------
Chapter 23 — Memory Regions: Stack, Heap, Arena
--------------------------------------------------------------------------------

Kru recognizes three memory regions. A value's region is part of how it
is declared, never inferred from usage.

STACK (the default)
    Every `let` and `var` binding is stack-allocated unless explicitly
    placed elsewhere. Stack values are destroyed automatically and
    deterministically when their scope ends (Chapter 28). No allocation
    call is ever implicit — consistent with "no implicit allocations"
    from Volume I.

HEAP (explicit only)
    Heap memory is requested explicitly through the standard library:

        let buf := kru::mem::Heap.alloc(1024)

    There is no implicit boxing, no hidden heap promotion of stack
    values, and no escape analysis that silently moves a value to the
    heap on the programmer's behalf. If a value is on the heap, a line
    of code said so.

ARENA (the preferred allocation mechanism)
    An `arena` is a scoped memory region that owns a block of storage
    and hands out allocations from it in O(1). Arenas are the idiomatic
    alternative to allocating and freeing objects one at a time:

        arena scratch {
            let a := scratch.alloc(Vertex)
            let b := scratch.alloc(Vertex)
            // ... use a, b ...
        } // entire arena released here, in one operation

    All memory owned by an arena is released together when the arena's
    scope closes. Objects inside an arena do not need individual
    destructors to reclaim their storage (though Chapter 28 explains
    what still runs before that release).

--------------------------------------------------------------------------------
Chapter 24 — Ownership Without a Borrow Checker
--------------------------------------------------------------------------------

Kru deliberately does not implement a Rust-style borrow checker with
programmer-facing lifetime parameters ('a, 'b, ...). That machinery is
a large part of what Volume I's Preface calls out as "artificial
complexity." Instead, Kru gets its safety from a narrower, cheaper-to-
reason-about rule:

    A reference may never outlive the region it was derived from.

This is enforced by SCOPE NESTING, not by general lifetime inference:

  - A reference into the stack is valid only within the function scope
    (or nested block) that produced it.
  - A reference into an arena is valid only within that arena's scope.
  - A reference into the heap is valid until explicitly freed, and the
    compiler cannot prove heap validity — see Chapter 26.

Because the rule is "does not outlive its enclosing scope" rather than
"satisfies an inferred lifetime relationship between arguments and
return values," the compiler's job is a straightforward nesting check,
not unification. The trade-off is real: patterns that require returning
a reference out of the scope that created it (which a full borrow
checker can sometimes prove sound) require an explicit `arena` promoted
to an outer scope, or a heap allocation, in Kru. Kru chooses
predictability over expressiveness here, on purpose.

MOVE SEMANTICS

    When a value is assigned to a new binding or passed to a function
    by value, it is MOVED — the new binding takes ownership, and the
    old binding is no longer usable:

    let a := String.from("hello")
    let b := a              // a is moved into b
    pr(a)                   // error: a has been moved

    Moves apply to types that own resources (String, Vector, heap
    allocations, file handles). Types that implement the Copy trait
(Chapter 32) are COPIED instead of moved — this includes all primitive
    types, bool, char, and structs whose fields are all Copy.

COPY TRAIT
    A type implements `Copy` if it is safe to bitwise-copy its
    representation. All primitive types implement Copy by default.
    User-defined structs must explicitly opt in:

    impl Copy for Point2D { }

    The compiler verifies that all fields of a Copy type are
    themselves Copy. A type containing a String, Vector, or any heap-
    owning type cannot implement Copy.

--------------------------------------------------------------------------------
Chapter 25 — Aliasing
--------------------------------------------------------------------------------

Within a single function body, Kru enforces:

    ALIASING XOR MUTABILITY
    At any program point, a value has either exactly one live mutable
    reference, or any number of live immutable references — never both.

This is checked by local flow analysis inside each function — it does
not require lifetime annotations, because it never has to reason across
function boundaries: a reference cannot outlive its scope (Chapter 24),
so aliasing conflicts cannot be hiding in a caller the analysis hasn't
seen.

    var total := 0
    let r := ref total          // immutable read reference
    total = total + 1           // error: `total` is mutably accessed
                                // while `r` is still live

    let mr := mut ref total     // mutable reference
    let r2 := ref total         // error: cannot create immutable ref
                                // while `mr` is live

Raw pointers obtained inside `unsafe` (Chapter 27) are exempt from this
rule — that exemption is the entire reason `unsafe` exists.

--------------------------------------------------------------------------------
Chapter 26 — Pointer Validity and @
--------------------------------------------------------------------------------

Chapter 10 introduced `@` as an explicit, visible memory read. This
chapter completes it.

    pointer@

is only legal outside `unsafe` when the compiler can prove, from
Chapters 24-25's scope/aliasing tracking, that `pointer` still refers to
live storage at that program point. If the arena or stack frame that
produced `pointer` has already closed, `pointer@` is a COMPILE ERROR,
not a runtime crash:

    error: use of reference after its region ended

      arena a {
          let p := a.alloc(Value)
      }
      let x := p@
                ^ `p` was derived from arena `a`, which closed above

Kru does not insert implicit null checks or bounds checks to make this
"safe at runtime instead" — per Principle IV (Zero-Cost Abstractions),
a validity guarantee is either proven at compile time or it is the
programmer's explicit responsibility inside `unsafe`. There is no third,
hidden option where the compiler quietly inserts a runtime check on your
behalf.

ARRAY INDEXING is the one narrow exception the standard library may
apply by default (`arr[i]`, bounds-checked), because that check is
against a length carried alongside the array itself, not a proof about
a separate region's lifetime — and it can be disabled explicitly via an
`unsafe` unchecked-index call for hot loops where the bound has already
been proven by the programmer.

RAW POINTERS
    Everything above describes `ref T` / `mut ref T`, which Chapters
    24-25's scope and aliasing tracking can reason about because every
    `ref` is derived, in source, from a traceable arena or stack
    binding. A raw pointer, type `*T`, is different: it carries none
    of that provenance. It may come from a heap allocator, from
    pointer arithmetic, or from FFI (Appendix C) — sources the
    compiler cannot follow back to a scope that proves liveness.

    Consequently, for `*T`:
      - Naming `*T` as a type (a struct field, a function signature)
        is ordinary code and needs no `unsafe`.
      - Producing a `*T` value from anything other than another `*T`
        you already hold (a heap allocation, `&raw` on a place,
        pointer arithmetic, an FFI return value) requires `unsafe`.
      - `pointer@` where `pointer` has type `*T` always requires
        `unsafe` — Chapters 24-25's proof machinery does not run on
        raw pointers at all, so the "provable outside unsafe" escape
        hatch earlier in this chapter never applies to them. This is
        the case the grammar's `pointer_type` production (Appendix
        A.4) marks "only valid in unsafe context."

    A raw pointer MAY be null — this is the one place in Kru where a
    value can meaningfully fail to point anywhere, because the
    compiler makes no liveness claim about it in the first place.
    `null` (Chapter 6) is a literal valid only where a `*T` type is
    expected, for exactly this purpose:

        let p: *i32 := mem_alloc(4)
        if p == null {
            panic("allocation failed")
        }

    This is deliberately narrower than `Option<T>`, which remains the
    idiomatic way to express "no value" everywhere else in the
    language (Chapter 18). `null` does not generalize to other types,
    does not participate in `match` the way `Option` does, and exists
    only because raw pointers are already an unsafe-adjacent escape
    hatch with no compile-time liveness proof to hang an `Option`-style
    guarantee on. Prefer `Option<ref T>` or `Option<*T>` at API
    boundaries; reach for a bare nullable `*T` only at the FFI/
    allocator layer where the null check is doing real, load-bearing
    work rather than standing in for `Option`.

--------------------------------------------------------------------------------
Chapter 27 — unsafe
--------------------------------------------------------------------------------

    unsafe {
        // Chapters 24-26's static checks are suspended in this block
    }

Inside `unsafe`, Kru permits:

  - constructing a `*T` raw pointer (from an allocator, `&raw`, or FFI)
  - raw pointer arithmetic
  - dereferencing (`@`) a `*T`, or a `ref T` the compiler cannot prove
    is still valid (Chapter 26)
  - unchecked array access
  - manual casts that bypass the type system's normal guarantees
  - calling external C functions via FFI

`unsafe` does not disable the type system generally — only the memory-
validity and aliasing analysis from this volume. Everything else
(exhaustive `match`, type checking, `ret` requirements) still applies
inside an `unsafe` block.

`unsafe` is the seam where the language stops proving things and the
programmer starts. It is never required for ordinary Kru code —
networking, parsing, data structures built on arenas, and application
logic should not need it. That is the actual, checkable version of
"security by default": not that unsafe operations are impossible, but
that they are impossible to reach BY ACCIDENT.

--------------------------------------------------------------------------------
Chapter 28 — Deterministic Destruction
--------------------------------------------------------------------------------

STACK values are destroyed in reverse declaration order when their
scope exits — no garbage collector, no finalizer queue, no pause.

ARENAS release their entire backing block in one operation when their
scope exits. Individual values inside an arena are not destructed one
at a time by default — this is what makes arena allocation cheap.

DESTRUCTOR METHODS
    A type may define a `drop` method that runs before its storage is
    reclaimed:

    impl File {
        fn drop(mut ref self) {
            self.handle.close()
        }
    }

    The `drop` method is called automatically when the value goes out
    of scope. It receives a `mut ref self` and returns void. A type's
    `drop` runs once, exactly when the value's scope ends.

    Inside an arena, `drop` methods do NOT run by default (the arena
    reclaims storage in bulk). Types that require cleanup must be
    allocated on the stack or heap instead, or the arena must be
    annotated to run destructors (future revision).

SECURE STRUCTS (values marked with the `secure` keyword from Volume I,
Principle VI) are the one case where per-value cleanup still runs even
inside an arena: their backing memory is explicitly overwritten before
release. This is the mechanism behind "automatic memory wiping for
sensitive structs" — it is a specific, opt-in destructor-time hook, not
a hidden cost paid by every value in the language.

--------------------------------------------------------------------------------
Chapter 29 — Undefined Behavior
--------------------------------------------------------------------------------

Kru's UB surface is deliberately small and entirely fenced behind
`unsafe`:

    A Kru program that contains no `unsafe` block cannot exhibit
    memory-corruption undefined behavior.

This is the precise, defensible version of the "prevents RCEs" claim
from Volume I: it is a claim about the safe subset of the language, not
the language as a whole.

Inside `unsafe`, the following remain undefined behavior and are the
programmer's responsibility to avoid:

  - dereferencing a pointer to storage that has been released
  - data races: unsynchronized concurrent mutable access from multiple
    threads (see the Concurrency chapter, Volume V)
  - casts that violate a type's required alignment
  - reading uninitialized memory as if it were initialized

--------------------------------------------------------------------------------
Chapter 30 — Alignment & Layout
--------------------------------------------------------------------------------

By default, struct fields are laid out in declaration order, with no
compiler-chosen reordering — consistent with Principle VII
(Deterministic Compilation): the same struct definition always produces
the same layout for a given target and compiler version.

    struct Header {
        magic: u32
        version: u16
        flags: u16
    }
    // magic at offset 0, version at offset 4, flags at offset 6

The compiler may insert padding between fields to satisfy alignment
requirements. It may NOT reorder fields.

EXPLICIT LAYOUT
    A `layout` attribute is reserved for explicit packing/alignment
    control (e.g. matching an external binary format):

    #[layout(packed)]
    struct UdpHeader {
        src_port: u16
        dst_port: u16
        length: u16
        checksum: u16
    }

    Full layout attribute syntax is deferred to Appendix C (ABI).

SIZEOF AND ALIGNOF
    The comptime functions `size_of<T>()` and `align_of<T>()` return
    the size and alignment of a type. These are only usable in
    `comptime` contexts:

    const HEADER_SIZE: u32 := comptime { size_of<Header>() }

--------------------------------------------------------------------------------
Chapter 31 — Summary of Guarantees
--------------------------------------------------------------------------------

    Outside unsafe:
      - no use-after-free (Chapter 24, 26)
      - no aliasing violations (Chapter 25)
      - no dangling @ reads (Chapter 26)
      - deterministic destruction order (Chapter 28)
      - bounds-checked array access (Chapter 26)

    Inside unsafe:
      - the programmer takes over all of the above
      - everything else (typing, exhaustiveness, ret) still holds

================================================================================
VOLUME IV — GENERICS & TRAITS
================================================================================

Volume II Chapter 21 established that Kru generics are resolved entirely
by monomorphization — no vtables, no boxing, no runtime type checks. This
volume adds the one thing that model was missing: a way to say what a
type parameter must support, without opening the door to dynamic
dispatch.

--------------------------------------------------------------------------------
Chapter 32 — Traits
--------------------------------------------------------------------------------

A `trait` declares a set of function signatures a type may implement.
A trait is never a value, never a pointer, and never carries a vtable —
it exists purely as a compile-time constraint.

    trait Addable {
        fn add(self, other: Self) -> Self
    }

`Self` inside a trait body refers to whichever concrete type ends up
implementing it — resolved at monomorphization time, exactly like the
`T` in Chapter 21's `identity<T>`.

BUILT-IN TRAITS
    The following traits are defined by the standard library and are
    available without import:

    Copy        bitwise copy is safe (Chapter 24)
    Clone       explicit deep copy via .clone()
    PartialEq   equality comparison via == and !=
    Comparable  ordering via <, >, <=, >=
    Display     convert to str for printing
    Debug       convert to str for debugging
    Error       base trait for error types (Chapter 18)
    Iterable    types that support `for` loops via .iter()/.next() (Chapter 19)

    Primitive types implement Copy, Clone, PartialEq, Comparable, and
    Display by default.

--------------------------------------------------------------------------------
Chapter 33 — impl
--------------------------------------------------------------------------------

A concrete type satisfies a trait through an `impl` block:

    struct Vector2 {
        x: f32
        y: f32
    }

    impl Addable for Vector2 {
        fn add(self, other: Self) -> Self {
            ret Vector2 { x: self.x + other.x, y: self.y + other.y }
        }
    }

`impl` blocks may also attach methods to a type directly, with no trait
involved — this is the formal home for the method syntax shown in
Chapter 16:

    impl Person {
        fn is_adult(self) -> bool {
            ret self.age > 18
        }
    }

DERIVE ATTRIBUTE
    Common trait implementations can be derived automatically using
    the `#[derive]` attribute:

    #[derive(Copy, Clone, PartialEq, Debug)]
    struct Point {
        x: i32
        y: i32
    }

    The compiler generates the impl blocks for the listed traits.
    Derive is only available for traits the compiler knows how to
    auto-implement (Copy, Clone, PartialEq, Debug, Display).

--------------------------------------------------------------------------------
Chapter 34 — Constraints on Generic Parameters
--------------------------------------------------------------------------------

A generic parameter may require one or more traits:

    fn sum<T: Addable>(a: T, b: T) -> T {
        ret a.add(b)
    }

    fn clamp<T: Addable + Comparable>(value: T, lo: T, hi: T) -> T {
        // both bounds available on T inside this function body
    }

The compiler checks the constraint AT EACH MONOMORPHIZATION SITE — that
is, when `sum<Vector2>` is instantiated, the compiler verifies `Vector2`
has an `impl Addable`. There is no separate "does T satisfy the trait"
proof obligation floating independently of a concrete call site, which
keeps error messages traceable to one instantiation (Principle V):

    error: Vector2 does not implement Addable

      24 | let total := sum(a, b)
                          ^^^ sum<Vector2> requires Addable

    Vector2 has no `impl Addable for Vector2`.

    Fix: add
        impl Addable for Vector2 { fn add(self, other: Self) -> Self { ... } }

--------------------------------------------------------------------------------
Chapter 35 — No Dynamic Dispatch (by default)
--------------------------------------------------------------------------------

Kru traits are a STATIC-DISPATCH-ONLY mechanism in 0.1 Alpha. There is
no `dyn Trait`, no trait object, no vtable — every call through a trait
bound is resolved to one concrete function at compile time, during
monomorphization, exactly like any other generic call.

This is a direct consequence of Principle IV (Zero-Cost Abstractions):
a vtable call is a runtime indirection the programmer did not ask for
explicitly. A future dynamic-dispatch mechanism is not ruled out, but it
would need its own explicit syntax (so the indirection is visible at the
call site) rather than reusing `trait` — see Volume XII, Future.

--------------------------------------------------------------------------------
Chapter 36 — Specialization
--------------------------------------------------------------------------------

Multiple `impl` blocks may exist for the same trait across different
types — that is the normal case, not "specialization" in the Rust sense.
True specialization (a generic `impl<T> Trait for T` overridden by a
more specific `impl Trait for Vector2`) is DEFERRED — not part of 0.1
Alpha. Blanket `impl<T>` blocks are not yet legal; every `impl` must
name one concrete type. This keeps trait resolution a simple lookup
(concrete type -> impl) rather than a most-specific-match search, which
matters for keeping diagnostics traceable per Principle V.

--------------------------------------------------------------------------------
Chapter 37 — Compile-Time Optimization Interplay
--------------------------------------------------------------------------------

Because trait calls are resolved during monomorphization (Chapter 34)
and `comptime` blocks (Volume II, Chapter 22) run after that resolution,
a `comptime` block may call trait methods on a concrete type exactly as
ordinary code would — the compiler already knows which `impl` applies,
so there is nothing special-cased about calling `a.add(b)` inside
`comptime` versus outside it.

--------------------------------------------------------------------------------
Chapter 38 — Reflection (Reserved, Non-Normative)
--------------------------------------------------------------------------------

A future revision is expected to add limited compile-time reflection —
e.g. enumerating a struct's fields inside `comptime` for serialization
code generation. No syntax is locked in for 0.1 Alpha. The namespace
`kru::meta` is reserved so that early standard-library code does not
collide with whatever this becomes.

--------------------------------------------------------------------------------
Chapter 39 — Metaprogramming (Reserved, Non-Normative)
--------------------------------------------------------------------------------

Kru has no macro system in 0.1 Alpha, and none is implied by anything
in this volume — this is intentional, per the Preface's rejection of
"complex macros and preprocessors" as a source of artificial complexity.
Whatever metaprogramming Kru eventually gets (if any) will be justified
against the Final Rule in Volume I on its own merits, not grandfathered
in because C++ and Rust have one.

================================================================================
VOLUME V — THE COMPILER
================================================================================

Volumes I-IV specify the language. This volume specifies the tool that
implements it — the actual thing you will eventually sit down and write.
Every static guarantee promised in Volumes II-IV (exhaustive match,
aliasing-XOR-mutability, scope-bound references, trait resolution) has
to be enforced by a specific stage below; this volume says which stage
enforces what, so there is no ambiguity about where a given check lives
once implementation starts.

--------------------------------------------------------------------------------
Chapter 40 — Pipeline Overview
--------------------------------------------------------------------------------

    source (.kru / .krux)
        |
        v
    LEXER            -- text -> token stream
        |
        v
    PARSER           -- tokens -> AST
        |
        v
    SEMANTIC ANALYSIS -- name resolution, type check, trait check,
        |                aliasing/lifetime check (mutates nothing;
        |                only annotates and rejects)
        v
    HIR              -- desugared, monomorphized (generics expanded)
        |
        v
    MIR              -- control-flow graph; dataflow-based checks;
        |                arena/aliasing analysis runs precisely here
        v
    KRU OPTIMIZATION -- target-independent MIR/HIR optimization
        |
        v
    TARGET LOWERING  -- ABI, instruction selection, registers, layout
        |
        v
    NATIVE EMISSION  -- machine code + object/executable format

Every stage is a pure function of the stage before it plus compiler
flags — no stage reads global mutable state, which is what makes
Principle VII (Deterministic Compilation) enforceable rather than
aspirational (see Chapter 50).

--------------------------------------------------------------------------------
Chapter 41 — Lexer
--------------------------------------------------------------------------------

The lexer turns UTF-8 source text into a flat token stream. Token kinds
map directly onto Volume II:

    KEYWORD      one of Chapter 6's reserved words
    IDENT        Chapter 7 identifier rules
    INT_LIT      123, 0xFF, 0b1010, 0o777, 1_000_000
    FLOAT_LIT    1.0, 3.14, 2.5e10
    STR_LIT      "..." (with escape sequences) or r"..." (raw)
    CHAR_LIT     '...'
    BOOL_LIT     true, false
    OPERATOR     Chapter 11's operator set, plus :=, @, ref, ?
    PUNCT        ( ) { } [ ] , . : ; .. | =>
    COMMENT      // and /* */ discarded; /// retained for docs

The lexer is a single left-to-right pass with one token of lookahead —
Kru's grammar was kept simple enough (Chapter 5) that no lexer hack
(like C's typedef problem) is required. Lexer errors follow the same
three-part diagnostic shape as every other error in Kru (Principle V):
what was found, why it's invalid, and the fix.

    error: unterminated string literal

      8 | let name := "Kru
                       ^ string starts here and is never closed

    Fix: add a closing "

--------------------------------------------------------------------------------
Chapter 42 — Parser
--------------------------------------------------------------------------------

Kru uses a hand-written RECURSIVE DESCENT parser for statements and
declarations, and a PRATT PARSER (operator-precedence parser) for
expressions, driven directly by Chapter 11's precedence table. A
hand-written parser (rather than a generated LALR/LR parser) was chosen
because Principle V requires error messages tied to exactly where
parsing failed and what was expected — generated parsers make that
harder to control precisely.

The parser produces the AST directly; there is no separate concrete
syntax tree (CST) stage, since Kru has no macro system (Volume IV,
Chapter 39) that would need to operate on un-desugared syntax.

--------------------------------------------------------------------------------
Chapter 43 — AST
--------------------------------------------------------------------------------

Representative node shapes (illustrative, not a final implementation
schema):

    FunctionDecl   { name, params, return_type, body, is_pub, is_inline, is_comptime }
    StructDecl     { name, fields, is_secure }
    EnumDecl       { name, variants, backing_type? }
    TraitDecl     { name, methods }
    ImplBlock      { trait_name?, target_type, methods }
    LetBinding     { name, type?, value, mutable: bool }
    VarBinding     { name, type?, value }
    MatchExpr      { scrutinee, arms }
    ArenaBlock     { name, body }
    UnsafeBlock    { body }
    WhileExpr      { condition, body }
    LoopExpr       { body, label? }
    BreakExpr      { label? }
    ContinueExpr   { label? }
    ClosureExpr    { params, capture_list, return_type, body }
    RefExpr        { target, is_mut }
    DerefExpr      { target }              // the `@` operator
    CallExpr       { callee, args, generic_args }
    IndexExpr      { target, index }
    SliceExpr      { target, range }
    CastExpr       { target, target_type }
    PropExpr       { expr, code }          // expr? propagation

Every AST node carries a source span (file, line, column range) so that
every later stage can still point at the original source text in its
diagnostics — a span is never dropped, only threaded through.

--------------------------------------------------------------------------------
Chapter 44 — Semantic Analysis
--------------------------------------------------------------------------------

Semantic analysis is where most of Volumes II-IV's promises are actually
checked, in this order:

  1. NAME RESOLUTION — every identifier resolves to exactly one
     declaration in scope; shadowing (Chapter 8) is legal, use of an
     undeclared name is not.
  2. TYPE CHECKING — literal/expression types are inferred or checked
     against declared types; `ret` expressions are checked against the
     function's declared return type; `match` exhaustiveness (Chapter
     15) is verified against the enum/struct's known variant set.
  3. MOVE TRACKING — the compiler tracks which bindings have been moved
     and rejects use-after-move (Chapter 24). Copy types are exempt.
  4. TRAIT RESOLUTION — every generic call site with a `T: Trait` bound
     (Chapter 34) is checked against the concrete type's known `impl`s.
  5. ALIASING & LIFETIME CHECKING — Volume III's rules (scope-bound
     references, aliasing-XOR-mutability, `@` validity) are checked here
     structurally on the AST for the straightforward cases, and handed
     to MIR (Chapter 46) for the cases that need real control-flow
     information (loops, early returns, branching aliasing).

Semantic analysis never modifies the AST — it only accepts, rejects,
and annotates it with resolved types and bindings for the next stage
to consume.

--------------------------------------------------------------------------------
Chapter 45 — HIR (High-Level IR)
--------------------------------------------------------------------------------

HIR is the AST with all language-level sugar removed and all generics
resolved:

  - every generic call (Chapter 21, 34) is replaced by a call to its
    monomorphized instantiation (`sum<Vector2>` becomes a direct call
    to a freshly generated `sum__Vector2`)
  - `impl` method calls are resolved to a specific function symbol —
    there is no dispatch left to do at this point, consistent with
    Volume IV Chapter 35 (no dynamic dispatch)
  - `impl` blocks and inline struct methods (Chapter 33) are normalized
    to the same representation
  - `?` propagation operators (Chapter 18) are lowered to explicit
    match expressions
  - compound assignment operators (Chapter 11) are lowered to
    `x = x OP y` form
  - `while` loops are lowered to `loop` + `if` + `break`

HIR is still expression-oriented and still fairly close to source; it
exists mainly to give monomorphization one clear place to happen, rather
than smearing it across the parser or the backend.

--------------------------------------------------------------------------------
Chapter 46 — MIR (Mid-Level IR)
--------------------------------------------------------------------------------

MIR lowers HIR into a control-flow graph of basic blocks — this is the
representation Chapter 24-26's static memory checks are formally defined
over, because "does this reference outlive its region" and "is there a
live mutable alias" are dataflow questions that need real control flow
(branches, loops, early `ret`) to answer precisely, not just AST
structure.

    bb0:
        t0 = arena.alloc(Value)
        goto bb1
    bb1:
        t1 = load t0          // requires: arena live at bb1 -- checked
        ret t1

The arena-liveness and aliasing checks from Volume III run as dataflow
analyses over this graph. This is also where `unsafe` blocks (Chapter
27) are marked as regions where the analysis's rejections become
warnings-only (or are skipped entirely) rather than hard errors.

--------------------------------------------------------------------------------
Chapter 47 — Direct Native Backend
--------------------------------------------------------------------------------

Kru's canonical production backend emits native machine code directly.
MIR is lowered by Kru-owned target backends that perform ABI lowering,
instruction selection, register assignment/allocation, stack-frame layout,
relocation generation, and object/executable emission. LLVM, libgccjit,
libclang, and other external compiler frameworks are not required by the
language or by the canonical compiler architecture.

This is a deliberate consequence of Principles III, IV, and VII: Kru aims
to make generated behavior inspectable, deterministic, and under the same
engineering control as the language frontend. It is also deliberately
scoped: a target backend is added only when Kru can test and maintain it.
A small, correct backend for one architecture is preferred over silently
delegating semantics to a large external compiler framework.

The bootstrap compiler MAY retain a C-output backend as a portability,
debugging, and conformance reference path. That path is not the definition
of Kru code generation and is not the intended final production path.

The first canonical native target is x86-64 Linux using the System V ABI.
Additional targets define their ABI, calling convention, relocation model,
object format, and instruction-selection rules explicitly (Chapter 105).
Unsupported target/language combinations must be rejected; a backend must
never silently miscompile an AST shape it does not implement.

Arena allocation (Chapter 23) lowers to a bump-pointer operation plus the
required backing-region bound/growth policy rather than a general-purpose
per-object allocator call. Exact growth policy is an implementation detail
only where it does not change the programmer-visible allocation semantics.

--------------------------------------------------------------------------------
Chapter 48 — Optimization
--------------------------------------------------------------------------------

Kru owns its target-independent optimization pipeline. Optimizations such
as constant folding, dead-code elimination, local inlining decisions,
control-flow simplification, and loop transforms operate on HIR/MIR before
target lowering. Target backends may then apply architecture-specific
peephole and instruction-selection improvements, but optimization must not
change Kru's observable semantics or weaken its safety checks.

  - COMPTIME FOLDING — `comptime { ... }` blocks (Chapter 22) are fully
    evaluated during compilation by the interpreter described in
    Chapter 49, and their result is substituted as a constant before
    target lowering.
  - MONOMORPHIZATION DEDUPLICATION — if two call sites instantiate the
    identical generic specialization (e.g. `sum<i32>` called from two
    places), only one copy is emitted.
  - INLINE HINT PROPAGATION — `inline fn` (Chapter 12) is carried into
    Kru's optimization pipeline as a hint, not a forced inline; the
    compiler is free to decline it, consistent with Chapter 12's wording.
  - ZERO-COST DROP — if a value's `drop` method is empty or its effects
    are provably unnecessary (e.g. a stack value with no resource
    handles), the call is elided entirely.

--------------------------------------------------------------------------------
Chapter 49 — Compile-Time Execution Sandbox
--------------------------------------------------------------------------------

`comptime` (Chapter 22) needs somewhere to actually run during
compilation. That somewhere is a SANDBOXED BYTECODE INTERPRETER, not
the host machine's native execution — this matters
because a sandboxed interpreter can enforce Principle VII by
construction rather than by convention:

  - no syscalls are reachable from `comptime` code (no filesystem, no
    network, no clock) unless a future revision adds an explicit,
    clearly-marked non-deterministic intrinsic
  - execution is deterministic given the same input MIR, independent of
    host OS, host architecture, or wall-clock timing
  - a `comptime` block that would loop forever is caught by a compile-
    time step limit, reported as a normal three-part diagnostic rather
    than hanging the compiler

--------------------------------------------------------------------------------
Chapter 50 — Determinism Enforcement
--------------------------------------------------------------------------------

Principle VII is enforced structurally, not by discipline:

  - every compiler-internal map/set that affects emitted code iterates
    in a defined order (insertion order or sorted key order — never
    hash-iteration order, which varies by process)
  - no absolute file paths, timestamps, or environment variables are
    embedded in the output binary unless the programmer explicitly
    requests them via a documented build-info intrinsic
  - monomorphization order (Chapter 45) is a deterministic function of
    source order, not of which thread finished compiling which module
    first, even under a parallel compiler frontend

--------------------------------------------------------------------------------
Chapter 51 — Incremental Compilation
--------------------------------------------------------------------------------

Each module's HIR is cached, keyed by a content hash of its own source
plus the resolved identity of everything it imports. A change to one
`.kru` file invalidates that module's cache entry and any module whose
monomorphized instantiations depended on a changed generic — the cache
key intentionally includes which concrete type parameters were used
against a given generic, since Chapter 45 makes each instantiation a
distinct emitted symbol.

--------------------------------------------------------------------------------
Chapter 52 — Self-Hosting
--------------------------------------------------------------------------------

Self-hosting (a Kru compiler written in Kru) is a long-term, non-
normative goal, not a 0.1 Alpha requirement. The bootstrap compiler
implementing everything in this volume is expected to be written in
whatever host language the implementer chooses; nothing in this Codex
requires the bootstrap compiler itself to be written in Kru. Self-
hosting becomes realistic only once Volume VI's standard library
(filesystem, string handling, data structures) is mature enough to
write a compiler with it.

Chapter 53 — Module Overview

    use kru::net

Chapter 54 — kru::mem
--------------------------------------------------------------------------------

    let region := kru::mem::Heap.alloc(1024)

--------------------------------------------------------------------------------
Chapter 55 — kru::io
--------------------------------------------------------------------------------

    kru::io::stdout().write("Hello")
    let line := kru::io::stdin().read_line()

`pr()` (used throughout the Codex) is standard-library sugar over
`kru::io::stdout().write_line()` — not a compiler intrinsic. This
matters for self-hosting (Chapter 52): `pr` is ordinary Kru code, not
magic the bootstrap compiler has to special-case forever.

    pr("Hello")              // prints with newline
    pr("Value: ", x)         // multiple arguments, space-separated

FORMATTED OUTPUT
    The `fmt` function provides inline formatting:

    pr(fmt("Port: {0}, Status: {1}", port, status))

    Format placeholders use {N} where N is the argument index (0-based).

--------------------------------------------------------------------------------
Chapter 56 — kru::fs
--------------------------------------------------------------------------------

    let file := kru::fs::open("config.toml")?
    let text := file.read_to_string()
    file.close()

File handles are ordinary structs with `impl` blocks (Volume IV); there
is no hidden RAII magic beyond what Chapter 28 (Deterministic
Destruction) already guarantees for any stack-held value. The `drop`
method on a File closes the handle if it hasn't been closed already.

--------------------------------------------------------------------------------
Chapter 57 — kru::net
--------------------------------------------------------------------------------

    let server := kru::net::Server.new("0.0.0.0:8080")

    server.listen(fn(req) [ref server] {
        ret kru::net::Response.ok("Hello")
    })

TCP/UDP primitives sit underneath the higher-level `Server`/`Response`
API shown above; raw socket access remains available for anything the
higher-level wrapper doesn't cover.

--------------------------------------------------------------------------------
Chapter 58 — kru::thread & kru::sync
--------------------------------------------------------------------------------

    let handle := kru::thread::spawn(fn() [] {
        pr("running on another thread")
    })
    handle.join()

    let counter := kru::sync::Atomic.new(0)
    counter.fetch_add(1)

Volume III, Chapter 29 named unsynchronized concurrent mutable access
as undefined behavior even inside `unsafe`; `kru::sync` (mutexes,
atomics, channels) is the sanctioned way to share mutable state across
threads without triggering it. A full concurrency memory model (what
synchronizes-with what) is deferred to a future revision of this
chapter, once threading is implemented enough to test against.

--------------------------------------------------------------------------------
Chapter 59 — kru::crypto
--------------------------------------------------------------------------------

    let digest := kru::crypto::sha256(data)
    let key    := kru::crypto::Secure.generate_key()

Anything handling key material is expected to be declared with the
`secure` keyword (Volume I, Principle VI; Volume III, Chapter 28) so
that its backing memory is wiped on destruction automatically, rather
than relying on the programmer to remember to zero it manually.

Chapter 60 — kru::db

================================================================================
VOLUME VII — SECURITY
================================================================================

Principle VI claimed security is "the default, not an add-on." This
volume is where that claim gets held to the same standard Volume III
held the memory claims to: every mechanism below is either something
the compiler enforces mechanically, or is explicitly marked as
best-effort hardening rather than a guarantee.

--------------------------------------------------------------------------------
Chapter 61 — The secure Keyword, Formally
--------------------------------------------------------------------------------

`secure` (reserved since Chapter 6) marks a struct whose backing memory
is overwritten before release, as introduced in Volume III, Chapter 28:

    secure struct Credentials {
        username: str
        password: SecureString
    }

Marking a struct `secure` is a promise the compiler enforces at every
exit path from its owning scope — normal fall-through, early `ret`,
and `unsafe`-triggered early exits all still run the wipe, because it
is inserted at the destructor point (Chapter 28), not on a single
"success" path a programmer could accidentally skip.

--------------------------------------------------------------------------------
Chapter 62 — SecureString
--------------------------------------------------------------------------------

`kru::crypto::SecureString` (Volume VI, Chapter 59) is a distinct type
from `str`, not a marker on top of it:

    let pw := SecureString.from("hunter2")

  - it is never implicitly printable — `pr(pw)` is a compile error,
    not a runtime redaction, because Principle IV means "safe by
    default" can't quietly cost a printf branch on every string in the
    program
  - it does not implement plain `str` equality/copy; comparing two
    `SecureString`s uses a constant-time comparison to avoid timing
    side-channels
  - its backing memory is wiped on destruction, same as any `secure`
    struct field

--------------------------------------------------------------------------------
Chapter 63 — Compile-Time Literal Encryption
--------------------------------------------------------------------------------

A string literal intended as a secret is stored as a SecureString,
not in the binary as plain text:

    let key := SecureString.from_encrypted("sk_live_abc123")

At compile time (via the `comptime` sandbox, Volume V Chapter 49), the
literal is encrypted into the binary's data section and decrypted into
`secure`-wiped memory only at first use — this defeats a static
`strings`-on-the-binary scan for embedded secrets, though it does not
and cannot defeat a determined attacker with a debugger attached to a
running process; the Codex makes that limit explicit rather than
implying otherwise.

This resolves a tension flagged back in Volume I review: Principle VI
wants secrets protected, Principle VII wants reproducible builds. The
resolution is that the encryption KEY IS ITSELF DETERMINISTIC BY
DEFAULT, derived from the compilation unit's content hash — so a build
with identical flags and source still produces an identical binary
(Principle VII holds). A programmer who wants the encrypted bytes to
differ across releases (so that leaked encryption logic from one
build doesn't help against another) opts in explicitly with a
build-time `--obfuscation-seed` flag — matching Chapter 50's rule
that randomness in Kru is always intentional, never accidental.

--------------------------------------------------------------------------------
Chapter 64 — Stack Cleaning & Register Clearing
--------------------------------------------------------------------------------

Any function whose body touches a `secure`-typed value gets additional
codegen at every return point: stack slots and registers that held the
secure value are explicitly zeroed before the function returns. This is
inserted only in functions that actually touch `secure` data — ordinary
functions pay nothing for it, which is the zero-cost-by-default version
of "clean up after yourself" rather than a blanket policy that would
slow down every function call in the program.

--------------------------------------------------------------------------------
Chapter 65 — Binary Hardening Defaults
--------------------------------------------------------------------------------

Kru does not invent new binary-hardening techniques — it turns the
well-established ones on by default, rather than requiring extra flags:

    stack protector          on by default
    position-independent exe  on by default (ASLR-compatible)
    RELRO (full)              on by default
    non-executable stack/heap on by default
    debug symbols in release  stripped unless explicitly requested

Every one of these is individually disable-able for embedded/kernel
targets (Volume I, Principle IX) where the target environment itself
manages these guarantees — but the OFF state always requires an explicit
flag; the ON state never does.

--------------------------------------------------------------------------------
Chapter 66 — Capability-Based Restrictions
--------------------------------------------------------------------------------

A project's manifest (formalized in Volume XI, package manager chapter)
may declare which standard-library modules a given source module is
permitted to `use`:

    capabilities {
        allow: [fs, io]
        deny:  [net]
    }

A `use kru::net` inside a module denied `net` is a compile error, not
a runtime permission check — consistent with Kru's general preference
(Volume III, Chapter 26) for proving things at compile time over
inserting runtime gates. This is aimed squarely at the plugin/third-
party-dependency case: a text-formatting library has no legitimate
reason to open a socket, and the capability system makes that a build
failure instead of a code-review hope.

--------------------------------------------------------------------------------
Chapter 67 — Summary: Safe by Default vs. Opt-In
--------------------------------------------------------------------------------

    On by default (no annotation needed):
      - binary hardening (Chapter 65)
      - aliasing/lifetime checking outside unsafe (Volume III)
      - bounds-checked array access (Chapter 26)

    On by explicit annotation (opt-in, zero-cost elsewhere):
      - secure struct / SecureString wiping (Chapter 61-62)
      - compile-time literal encryption (Chapter 63)
      - stack/register cleaning (Chapter 64)
      - capability restrictions (Chapter 66)

================================================================================
VOLUME VIII — KRU-X
================================================================================

Volume I, Principle X promised a co-equal frontend language sharing
Kru's compiler and philosophy. This volume specifies where Kru-X is
identical to Kru, and — just as important — the specific, small set
of places it deliberately diverges, and why.

--------------------------------------------------------------------------------
Chapter 68 — Why Kru-X Exists
--------------------------------------------------------------------------------

Application and UI code has different pressures than systems code: it
is written and rearranged far more often, its objects (windows,
widgets, components) have lifetimes tied to user interaction rather
than a predictable call stack, and its bugs are more often about state
management than raw performance. Forcing every button handler to
manually declare an `arena` (Volume III, Chapter 23) would satisfy
Principle II's letter while violating its spirit — "a beginner should
read a Kru program within minutes" doesn't hold if every UI callback
is buried in memory-region bookkeeping. Kru-X exists so that domain
gets ergonomics suited to it, without changing what Kru itself is.

--------------------------------------------------------------------------------
Chapter 69 — Relationship With Kru
--------------------------------------------------------------------------------

Kru-X source lives in `.krux` files (Chapter 4), compiles through the
same pipeline (Volume V) into the same Kru native backend, and links
against the same standard library (Volume VI) plus a Kru-X-specific
`kru-x::ui` module (Chapter 72). There is no separate Kru-X runtime —
"runtime" in the managed-language sense does not exist in either
language, per Volume I's rejection of virtual machines.

--------------------------------------------------------------------------------
Chapter 70 — Shared Syntax, One Deliberate Divergence
--------------------------------------------------------------------------------

Every construct from Volumes II-IV (let/var, ret, match, struct,
trait, impl, generics, ref, @) is identical in Kru-X — a Kru-X file
is readable by anyone who has read this far. The places Kru-X's
defaults diverge:

    1. COMPONENT-SCOPED ARENAS BY DEFAULT
    2. THE `component` KEYWORD

COMPONENT-SCOPED ARENAS BY DEFAULT

    In Kru-X, a UI component's fields are implicitly backed by an
    arena tied to that component's own lifecycle — created when the
    component mounts, released when it unmounts — without the
    programmer writing an explicit `arena { }` block. In plain Kru,
    arena scoping is always explicit (Volume III, Chapter 23).

THE `component` KEYWORD

    A struct marked with the `component` keyword is a Kru-X UI
    component. This is the ONLY struct type that receives the
    implicit component-scoped arena. Regular structs in `.krux` files
    behave exactly as in Kru — no implicit arena.

    component LoginWindow {
        title: str
        username: str
        attempts: i32
    }

    A `component` is a struct with additional semantics:

      - LIFECYCLE: A component has a mount/unmount lifecycle. When
        mounted, its implicit arena is created. When unmounted, the
        arena and all allocations within it are released in one
        operation (Volume III, Chapter 23).

      - STATE: Fields declared in a component are state — they persist
        across renders within the component's lifetime. Mutation of
        component state triggers a re-render (Chapter 72).

      - RENDER METHOD: A component must implement a `render` method
        via an `impl` block. This method is called by the UI runtime
        to produce the component's visual output.

        impl LoginWindow {
            fn render(ref self) {
                ui::column(fn() [ref self] {
                    ui::text(self.title)
                    ui::text_field("Username", ref self.username)
                    ui::button("Login", fn() [mut ref self] {
                        self.attempts += 1
                    })
                })
            }
        }

      - NESTING: Components may contain other components as fields.
        Child components are mounted when the parent mounts and
        unmounted when the parent unmounts — their arenas nest.

    NON-COMPONENT STRUCTS in `.krux` files are plain Kru structs.
    They do not receive an implicit arena, do not have a lifecycle,
    and do not trigger re-renders. They exist for data modeling
    within the application layer.

This is a genuine, acknowledged exception to Principle II's "nothing
unexpected occurs implicitly," justified entirely by Principle X:
Kru-X is allowed to specialize its defaults for its own domain,
precisely because Kru itself does not inherit this exception. The
`component` keyword makes the implicit arena opt-in: a programmer
who writes a plain `struct` in a `.krux` file gets exactly the same
behavior as in Kru. A Kru-X programmer who wants an arena with a
different lifetime than "this component" still reaches for an
explicit `arena` block, same as in Kru.

--------------------------------------------------------------------------------
Chapter 71 — Native Interoperability & .kh Bindings
--------------------------------------------------------------------------------

A Kru module can generate a `.kh` interface header describing its
public (`pub`) API surface:

    kru gen-header mymodule.kru  ->  mymodule.kh

Kru-X code imports it directly:

    use "mymodule.kh"

Because both languages share one ABI (formalized in Appendix C),
calling from Kru-X into Kru requires no marshaling layer, no
serialization, and no FFI boundary in the C sense — it is an ordinary
function call once the `.kh` header is generated.

--------------------------------------------------------------------------------
Chapter 72 — Desktop Targets
--------------------------------------------------------------------------------

`kru-x::ui` provides native widgets, layout, and an event loop
compiled directly to the host platform's windowing system — Kru-X does
not wrap a web view or an embedded browser engine to render desktop UI,
keeping it consistent with Volume I's rejection of unnecessary layers.

On Linux, `kru-x::ui` targets Wayland and X11 directly. On macOS, it
targets Cocoa. On Windows, it targets the Win32 API. Each backend is
a separate compilation target selected by the build system, not a
runtime abstraction layer.

--------------------------------------------------------------------------------
Chapter 73 — Web Targets
--------------------------------------------------------------------------------

The same `.krux` source can target WebAssembly through a dedicated Kru
WebAssembly lowering backend from MIR (Volume V, Chapter 46), rather than
through the native machine-code emitter.
Determinism (Chapter 50) is defined per-target: a wasm build is
reproducible against identical source/flags/target-triple, the same
way a native build is — the two are not required to produce identical
output as each other, only to each be reproducible.

--------------------------------------------------------------------------------
Chapter 74 — Future Mobile Targets (Reserved, Non-Normative)
--------------------------------------------------------------------------------

iOS and Android backends are future work. No API surface is locked
in for 0.1 Alpha; `kru-x::ui`'s desktop widget model is not assumed
to transfer directly, since mobile platform conventions (touch,
lifecycle suspension) differ enough to warrant their own review when
the time comes.

--------------------------------------------------------------------------------
Chapter 75 — Sandboxing
--------------------------------------------------------------------------------

Because Kru-X applications are, by definition, the most user-facing
and network-facing part of the ecosystem, they run under the
capability model (Volume VII, Chapter 66) by default with an EMPTY
grant: a Kru-X application declares every capability it needs
(filesystem, network, etc.) in its manifest, rather than starting
with full access and being expected to narrow it. This mirrors the
deny-by-default posture of mobile app sandboxing models, applied at
compile time rather than by an OS-level permission prompt.

END OF VOLUME VIII — KRU-X

================================================================================
VOLUME IX — COMPILER DIAGNOSTICS
================================================================================

Principle V states that the compiler exists to help. This volume
defines what "help" means in practice.

A Kru diagnostic is not merely a statement that compilation failed.
It is a structured explanation of:

    1. WHAT happened
    2. WHY it happened
    3. WHERE it happened
    4. HOW to fix it

A compiler error that only says "invalid syntax" has failed its
purpose.

--------------------------------------------------------------------------------
Chapter 76 — Diagnostic Philosophy
--------------------------------------------------------------------------------

Every diagnostic produced by the Kru compiler MUST be actionable.

A diagnostic should answer the question:

    "What does the programmer need to change?"

The compiler must prefer specific explanations over generic
classifications.

Bad:

    error: type mismatch

Good:

    error[K1002]: cannot assign f64 to i32

      12 | let count: i32 := 4.5
                         ^^^ expected i32

    Why:
        Floating-point values cannot be implicitly converted to
        integers.

    Fix:
        Use an explicit conversion:

            let count: i32 := cast<i32>(4.5)

The compiler must never assume programmer intent. It may suggest
likely solutions, but suggestions are not applied automatically
unless explicitly requested by tooling.

--------------------------------------------------------------------------------
Chapter 77 — Diagnostic Structure
--------------------------------------------------------------------------------

Every diagnostic consists of seven components:

    SEVERITY
        error, warning, note, help

    CODE
        A stable identifier (Chapter 79)

    MESSAGE
        A short description of the issue.

    LOCATION
        Source file, line, and column span.

    SOURCE CONTEXT
        The relevant source line(s) with a caret pointing at the
        issue.

    EXPLANATION
        Why the compiler rejected or warned about the code.

    SUGGESTED FIX
        One or more concrete corrections the programmer can apply.

The internal representation is:

    Diagnostic {
        severity
        code
        message
        primary_span
        related_spans
        notes
        suggestions
    }

The compiler must preserve source locations from lexing through
backend analysis. No compiler stage may discard location information.
A backend optimization failure must still be traceable to the
original source expression that caused it.

Example:

    error[K1004]: cannot modify immutable binding

      7 | let total := 0
      8 | total = 10
             ^^^^^

    `total` was declared using `let`.

    Immutable values cannot be assigned after initialization.

    Help:
        Change the declaration:

            var total := 0

--------------------------------------------------------------------------------
Chapter 78 — Diagnostic Severities
--------------------------------------------------------------------------------

Kru defines four diagnostic levels.

ERROR
    An error represents a condition that prevents valid compilation.
    Examples: undefined symbols, type mismatches, invalid memory
    access, exhaustiveness failures, invalid capability usage.

WARNING
    A warning represents valid code that may indicate a mistake.
    Warnings never prevent compilation unless promoted through
    project settings. Examples: unused variables, suspicious casts,
    performance issues, unreachable code.

NOTE
    Notes provide additional context for a parent error or warning.
    Notes cannot exist alone — they always attach to a primary
    diagnostic.

HELP
    Help messages provide optional improvement suggestions, including
    machine-applicable fixes. A fix contains an original source
    range, replacement text, and an explanation.

    Automatic fixes MUST NOT change program behavior. The compiler
    may remove unused imports, rename shadowed bindings, insert
    missing syntax, or replace unnecessary mutability. The compiler
    must not change algorithms, alter control flow, add allocations,
    or insert unsafe code.

--------------------------------------------------------------------------------
Chapter 79 — Diagnostic Codes
--------------------------------------------------------------------------------

Every diagnostic has a stable identifier.

Format:

    K<class><number>

Classes:

    K1xxx        Language errors (parser, type, name resolution)
    K2xxx        Warnings
    K3xxx        Memory system errors
    K4xxx        Security errors
    K5xxx        Compiler/toolchain errors

Examples:

    K1001        Unknown identifier
    K1002        Type mismatch
    K1004        Immutable binding modified
    K1005        Expected expression
    K1006        Impure expression in match guard
    K2001        Unused variable
    K2002        Missing documentation
    K2003        Match arm with always-false guard
    K2010        Unused mutable binding
    K2100        Repeated heap allocation in loop
    K3001        Reference lifetime violation
    K3002        Mutable access conflicts with active reference
    K3003        Escaping closure captures reference to local binding
    K3010        Cannot return reference to local value
    K4001        Capability violation
    K5001        Internal compiler error

Diagnostic numbers are permanent. Once assigned, a code is never
reused or reinterpreted. This allows IDE integration, documentation
lookup, automated tooling, and compiler testing.

Warning categories (subset of K2xxx):

    K2xxx        correctness
    K21xx        style
    K22xx        performance
    K23xx        security
    K24xx        compatibility

Warnings may be configured:

    kru build --deny K2300

turns a warning range into errors. The same source, compiler version,
and flags must produce the same diagnostics (Principle VII).

--------------------------------------------------------------------------------
Chapter 80 — Source Highlighting & Type/Memory Diagnostics
--------------------------------------------------------------------------------

Every diagnostic must highlight the smallest meaningful source region.
The compiler should avoid highlighting entire statements when a
smaller expression explains the issue.

TYPE DIAGNOSTICS must describe user concepts, not compiler internals.
The compiler must never expose internal names like TypeVariable<17>
or NodeId(492) or ConstraintFailure<T>.

    error[K1002]: incompatible types

      22 | let size: u64 := filename
                         ^^^^^^^^

    Expected:    u64
    Found:       str

    A string cannot be assigned to an integer.

    If conversion is intended:
        parse_u64(filename)

MEMORY DIAGNOSTICS are first-class errors. Because Kru provides
compile-time memory guarantees, memory violations should be detected
before execution whenever possible.

    error[K3001]: reference outlives owning region

      8 | let number := value@
                   ^^^^^

    `value` belongs to arena `temporary`.

    The arena ended here:
      6 | }
         ^

    Possible fixes:
        - Move the arena to an outer scope.
        - Copy the value before the arena closes.
        - Allocate in a longer-lived region.

    error[K3002]: mutable access conflicts with active reference

    Mutable access:
      6 | health = 50
              ^^^^^

    Existing reference:
      4 | let current := ref health
                    ^^^^^^^^^^

    Kru requires: multiple readers OR one writer, never both.

--------------------------------------------------------------------------------
Chapter 81 — Performance Diagnostics & Suggestions
--------------------------------------------------------------------------------

Performance is observable behavior in Kru. The compiler may provide
performance diagnostics:

    warning[K2100]: repeated heap allocation in loop

      50 | loop {
      51 |     let packet := Heap.alloc(Packet)
                         ^^^^^^^^^^^^^^^

    Allocation occurs inside a loop.

    Consider:
        arena packets {
            ...
        }

Performance warnings never change generated code. The programmer
remains in control.

SUGGESTIONS must satisfy:
    1. They must be correct.
    2. They must be optional.
    3. They must not hide important decisions.

The compiler may suggest: adding imports, changing binding type,
adding explicit conversions, removing unused code.

The compiler must never automatically: add unsafe, disable safety
checks, change ownership behavior, add hidden allocations.

--------------------------------------------------------------------------------
Chapter 82 — Error Recovery
--------------------------------------------------------------------------------

The parser attempts recovery after errors so multiple issues may be
reported in one compilation pass.

Recovery points:
    - statement boundaries
    - closing braces
    - declarations
    - match arms

Example:

    fn main() {
        let x :=
        let y := 5
    }

The parser reports:

    error[K1005]: expected expression after :=

and continues parsing `let y := 5` rather than terminating.

The compiler should report the earliest meaningful error, not every
possible consequence of the first error. A binding that failed to
initialize should not also produce an "unused variable" warning.

LINTS
    Lints are optional analysis rules that enforce project-specific
    standards. Unlike compiler errors, lints do not define Kru
    correctness. Project lint configuration belongs in `kru.toml`:

    [lint]
    unsafe = "deny"
    warnings = "error"
    naming = "strict"

    Standard lints: unused, naming, complexity, allocation, security,
    documentation. Third-party lint plugins are not supported in 0.1
    Alpha to preserve deterministic compilation.

--------------------------------------------------------------------------------
Chapter 83 — Internal Compiler Errors
--------------------------------------------------------------------------------

Compiler implementation failures are distinct from user errors.

Internal failures use:

    ICE — Internal Compiler Error

Example:

    internal compiler error [K5001]:
        failed to lower MIR block

An ICE must include:
    - compiler version
    - target triple
    - reproduction information
    - optional backtrace

The compiler must never present an ICE as if the user's program was
incorrect. An ICE is always a compiler bug, not a user error.

DIAGNOSTIC PHILOSOPHY SUMMARY

    1. Never blame the programmer.
    2. Never expose compiler implementation details.
    3. Always explain the machine's reasoning.
    4. Prefer prevention over runtime failure.
    5. Teach the language while compiling.

The compiler is not an obstacle between the programmer and the
machine. The compiler is the translator between human intent and
machine behavior.

END OF VOLUME IX — COMPILER DIAGNOSTICS

================================================================================
VOLUME X — STYLE & CONVENTIONS
================================================================================

Kru is designed so that source code communicates intent directly. This
volume defines the official conventions for writing Kru programs.

These rules do not change program meaning. They exist to make Kru code
consistent across projects, libraries, and the standard ecosystem.

The formatter (`kru fmt`) enforces formatting rules automatically.

--------------------------------------------------------------------------------
Chapter 84 — Official Formatting
--------------------------------------------------------------------------------

Kru source uses four-space indentation. Tabs are not permitted in
formatted Kru source.

Before formatting:

    fn calculate(x:i32,y:i32)->i32{
        ret x+y
    }

After formatting:

    fn calculate(x: i32, y: i32) -> i32 {
        ret x + y
    }

The formatter controls: indentation, spacing, line breaks, brace
placement, import ordering.

The formatter does not: rename identifiers, reorder statements, alter
comments, modify unsafe code.

Formatting must be deterministic: identical source + identical
formatter version produces identical formatted output.

--------------------------------------------------------------------------------
Chapter 85 — Documentation
--------------------------------------------------------------------------------

Documentation is written using triple-slash comments:

    /// Calculates the checksum of a packet.
    ///
    /// Returns an error if the packet is malformed.
    pub fn checksum(packet: Packet) -> Result<u32, Error> {
        ...
    }

Documentation comments attach to the declaration immediately
following them. Supported targets: modules, functions, structs,
enums, traits, public constants.

Public declarations SHOULD contain documentation. The compiler may
warn `K2002: missing documentation` when enabled by project lint
settings.

--------------------------------------------------------------------------------
Chapter 86 — Naming Rules
--------------------------------------------------------------------------------

See Chapter 7 for the complete naming convention table. The
formatter enforces naming as a lint, not as a parse error —
non-conforming names compile but produce a warning.

--------------------------------------------------------------------------------
Chapter 87 — Project Organization & Modules
--------------------------------------------------------------------------------

A Kru project follows a predictable layout:

    project/
    |
    |-- kru.toml
    |
    |-- src/
    |   |-- main.kru
    |   |-- lib.kru
    |
    |-- tests/
    |
    |-- examples/
    |
    |-- build/

The entry point is `src/main.kru` unless overridden by the project
manifest. Libraries use `src/lib.kru` which defines exported public
modules.

MODULES
    A Kru module is a compilation unit determined by a source file.
    No module declaration is required.

    File:           network/http.kru
    Creates module: network::http

    Imports follow the source tree:

    use network::http

    Modules should expose a small public interface. Public APIs should
    be intentionally small because every public symbol becomes a
    compatibility commitment.

IMPORT ORGANIZATION
    Imports are grouped in this order, alphabetically within each:

    1. Standard library     (use kru::net)
    2. Project modules       (use game::physics)
    3. External interfaces   (use "driver.kh")

    Unused imports are compiler warnings.

--------------------------------------------------------------------------------
Chapter 88 — Error Handling Style
--------------------------------------------------------------------------------

Kru prefers explicit error handling. Functions that may fail SHOULD
return `Result<T, E>` (Chapter 18). Silent failure is discouraged.

    fn open_config(path: str) -> Result<File, Error> {
        ret kru::fs::open(path)
    }

For unrecoverable failures, `panic()` may be used. It is intended
for impossible states, violated internal assumptions, and corrupted
program invariants — not normal error handling.

--------------------------------------------------------------------------------
Chapter 89 — Unsafe & Performance Style
--------------------------------------------------------------------------------

Unsafe blocks must be visually isolated and contain only the minimum
operations required:

    unsafe {
        let raw := ptr.add(offset)
        ret raw@
    }

Projects may require SAFETY documentation comments explaining why
the unsafe operation is valid.

Kru does not require premature optimization. The compiler performs
inlining, constant folding, dead-code removal, and monomorphization.
Programmers should optimize based on measured behavior, not
speculation. Avoid `unsafe`, manual memory tricks, and architecture-
specific code unless measurements justify them.

--------------------------------------------------------------------------------
Chapter 90 — Security Style
--------------------------------------------------------------------------------

Security-sensitive code should use explicit secure types:

    let password: SecureString

Avoid `let password: str` for values containing passwords,
cryptographic keys, authentication tokens, or private credentials.
Sensitive values should have the smallest possible scope.

--------------------------------------------------------------------------------
Chapter 91 — Code Review Expectations
--------------------------------------------------------------------------------

Official Kru projects SHOULD evaluate:

    Correctness:    Does the code behave correctly?
    Safety:         Are unsafe operations justified?
    Clarity:        Can another programmer understand intent?
    Performance:     Are allocations and copies intentional?
    Maintenance:    Is the public interface stable?

Kru favors code that explains itself over code that demonstrates
cleverness.

END OF VOLUME X — STYLE & CONVENTIONS
================================================================================

================================================================================
VOLUME XI — TOOLCHAIN
================================================================================

The Kru language is only one part of the ecosystem. This volume
specifies the official tools distributed with the Kru compiler.

The toolchain follows the same principles as the language:

    - deterministic behavior
    - useful diagnostics
    - explicit operations
    - minimal hidden behavior

The official toolchain consists of:

    kru          compiler and project manager
    kru fmt      formatter
    kru test     test runner
    kru doc      documentation generator
    kru lsp      language server
    kru dbg      debugger interface

Third-party tools may exist, but official tooling defines the
supported development experience.

--------------------------------------------------------------------------------
Chapter 92 — Package Manager
--------------------------------------------------------------------------------

Kru projects use the built-in package manager, invoked through:

    kru pkg <command>

A project is identified by its manifest:

    [package]
    name = "network_server"
    version = "1.0.0"

    [target]
    type = "binary"

    [dependencies]
    crypto = "1.2.0"

PACKAGE IDENTITY
    Every package has: name, version, source hash, and compiler
    compatibility version. A package identity is:

        package name + version + dependency graph + compiler version

    Two builds with identical package identities MUST produce
    identical dependency resolution.

DEPENDENCIES
    Dependencies are explicit. The compiler does not automatically
    download missing packages during compilation. Installing
    dependencies requires:

    kru pkg fetch

    This prevents builds from silently depending on network
    availability.

PACKAGE SOURCES
    Supported: local path, official registry, git repository.

    [dependencies]
    math = { path = "../math" }
    driver = { git = "example.com/device-driver", version = "1.0" }

    Remote dependencies are verified by content hash. A dependency
    changing its contents without changing its version is a package
    integrity failure.

LOCK FILE
    Kru uses a lock file `kru.lock` containing exact package
    versions, source hashes, and the dependency graph. Applications
    SHOULD commit `kru.lock`. Libraries MAY omit it. The compiler
    never silently upgrades dependencies.

--------------------------------------------------------------------------------
Chapter 93 — Build System
--------------------------------------------------------------------------------

    kru build

The build system performs: manifest loading, dependency resolution,
source discovery, compilation, linking, output generation.

BUILD PROFILES
    Debug: optimizations disabled, debug symbols enabled, faster
    compilation.

    Release: optimization enabled, debug symbols removed, binary
    hardening enabled.

    kru build --release

TARGETS
    A package may define multiple targets:

    [target]
    type = "binary"   // or "library"

    Executable entry points require: pub fn main() -> i32
    The return value becomes the process exit code.

COMPILER FLAGS
    Compiler options may be supplied through: command line,
    kru.toml, or environment configuration.

    kru build --target x86_64-linux
    kru build --release
    kru build --debug-symbols

    Flags affecting output are included in deterministic build
    identity.

--------------------------------------------------------------------------------
Chapter 94 — Language Server
--------------------------------------------------------------------------------

    kru lsp

The language server implements: diagnostics, completion, symbol
lookup, rename operations, formatting, documentation lookup.

The LSP uses the SAME compiler frontend as normal compilation. The
language server MUST NOT have separate parsing or type-checking
logic. This prevents "editor says valid, compiler says invalid"
situations.

INCREMENTAL ANALYSIS
    The language server maintains parsed AST, semantic information,
    and a dependency graph. Changes are analyzed incrementally — a
    single changed function should not require reparsing the entire
    project.

CODE COMPLETION
    Completion suggestions are based on visible scope, imported
    modules, available methods, and trait implementations. The language
    server does not suggest invalid programs.

--------------------------------------------------------------------------------
Chapter 95 — Debugger
--------------------------------------------------------------------------------

    kru dbg program

The debugger supports: breakpoints, stepping, stack inspection,
variable inspection, memory inspection, thread inspection.

Debug builds contain: source locations, variable names, type
information, stack mappings. Release builds remove this information
unless requested.

MEMORY INSPECTION
    The debugger understands Kru memory concepts. It displays stack
    values, heap regions, arena ownership, and references:

    reference:
        type: Packet
        region: arena connection_buffer
        valid: true

    The debugger does not bypass Kru safety rules. Unsafe memory
    inspection requires explicit debugger unsafe mode, which allows
    raw memory reads, pointer inspection, and invalid memory
    examination. Unsafe actions are marked explicitly in output.

--------------------------------------------------------------------------------
Chapter 96 — Testing Framework
--------------------------------------------------------------------------------

Kru includes a built-in testing system. Tests are declared using the
`test` keyword:

    test "addition works" {
        let result := add(2, 3)
        assert(result == 5)
    }

Tests compile as normal Kru code.

ASSERTIONS
    Built-in assertions:

    assert(condition)              // asserts a boolean is true
    assert_equal(a, b)            // asserts two values are equal
    assert_error(expression)      // asserts an expression returns Err

    Failed assertions produce compiler-style diagnostics:

    test failed: packet size
      expected:  64
      received:  32

TEST EXECUTION
    Run tests with `kru test`. Tests may execute in parallel.
    Ordering is undefined unless explicitly requested. Tests must not
    rely on execution order.

UNSAFE TESTS
    Unsafe code may be tested normally:

    test "allocator behavior" {
        unsafe {
            ...
        }
    }

    Unsafe failures are reported separately.

--------------------------------------------------------------------------------
Chapter 97 — Formatter
--------------------------------------------------------------------------------

    kru fmt

The formatter follows Volume X formatting rules. It guarantees
idempotency: running `kru fmt` twice produces identical output.

The formatter does not: execute code, resolve dependencies, or
modify semantics.

Configuration is stored in `kru.toml`:

    [format]
    line_width = 100

Projects SHOULD use the default formatter settings. Custom
formatting rules are intentionally limited to preserve ecosystem
consistency.

--------------------------------------------------------------------------------
Chapter 98 — Documentation Generator
--------------------------------------------------------------------------------

    kru doc

The documentation generator reads: public declarations, documentation
comments, type information, and examples.

Generated documentation includes: API reference, function signatures,
trait relationships, and source links. Private declarations are
excluded unless explicitly requested.

--------------------------------------------------------------------------------
Chapter 99 — Build Reproduction
--------------------------------------------------------------------------------

    kru reproduce

Records: compiler version, target, flags, dependency hashes, source
hashes. A project can verify: "Can this binary be recreated?"

The goal is not only reproducible compilation, but reproducible
investigation.

--------------------------------------------------------------------------------
Chapter 100 — Toolchain Stability
--------------------------------------------------------------------------------

The official toolchain follows semantic versioning: major.minor.patch

Major versions may contain breaking language changes.

Minor versions may add: standard library features, diagnostics,
tooling features. Minor versions must not silently change existing
language meaning.

Patch versions contain: bug fixes, diagnostic improvements,
performance improvements.

================================================================================
VOLUME XII — FUTURE
================================================================================

This volume defines the future direction of Kru.

Features listed here are not part of Kru 0.1 Alpha unless explicitly
stated elsewhere in this Codex. Reserved ideas exist to prevent future
design conflicts, not to promise implementation.

Future development follows the Final Rule:

    Does this make writing efficient systems software simpler without
    hiding how the machine works?

    If yes, it may belong in Kru.
    If no, it does not.

--------------------------------------------------------------------------------
Chapter 101 — Stability Policy
--------------------------------------------------------------------------------

ALPHA
    Alpha versions define the experimental foundation. During Alpha:
    syntax may change, APIs may change, compiler behavior may change,
    incomplete features may be removed. The Codex remains the source
    of truth even when compiler implementations differ.

BETA
    Beta versions freeze: core syntax, memory model, type system,
    module system, compiler guarantees. Breaking changes require
    explicit migration documentation.

STABLE
    Stable Kru guarantees: backwards compatibility, deterministic
    compilation behavior, stable standard library interfaces, stable
    ABI within supported targets. Breaking changes require a major
    version increment.

--------------------------------------------------------------------------------
Chapter 102 — Reserved Language Features
--------------------------------------------------------------------------------

Reservation does not mean approval.

PATTERN IMPROVEMENTS
    Future versions may expand pattern matching: range patterns
    (0..10), and additional destructuring improvements. Match guards
    (if conditions on arms) and alternation (|) are already
    supported in 0.1 Alpha. The current exhaustive match model
    remains unchanged.

ITERATOR SYSTEM
    The basic `for x in collection` loop is supported in 0.1 Alpha
    (Chapter 19). Future versions may add: lazy iterator adapters
    (map, filter, collect), custom iterator combinators, and
    parallel iteration. Any iterator system must compile into loops,
    direct calls, and no hidden allocation. A managed iterator object
    model is rejected.

ASYNC PROGRAMMING
    Asynchronous programming may be added for networking, IO, and
    distributed systems via compiler-generated state machines.
    Rejected: hidden runtime scheduler, mandatory garbage collection,
    opaque futures. Async behavior must remain visible in source.

REFLECTION
    Limited compile-time reflection may be added. Allowed: struct
    field discovery, enum variant discovery, serialization generation.
    Disallowed by default: runtime object inspection, dynamic type
    modification, reflection-based dispatch.

MACROS AND METAPROGRAMMING
    Kru has no macro system. Future metaprogramming must satisfy:
    deterministic expansion, clear diagnostics, no hidden language
    inside the language. Rejected: unrestricted text substitution,
    preprocessor-style macros, compile-time code with unrestricted
    system access.

--------------------------------------------------------------------------------
Chapter 103 — Rejected Designs
--------------------------------------------------------------------------------

Rejection is a language decision, not an implementation limitation.

GARBAGE COLLECTION — Rejected. Systems software requires predictable
memory behavior. Kru provides stack, heap, and arena instead.

RUNTIME VIRTUAL MACHINE — Rejected. Kru targets native execution.
A mandatory runtime would increase deployment complexity, hide
machine behavior, and add unavoidable overhead.

IMPLICIT ALLOCATIONS — Rejected. Converting strings automatically,
silently boxing values, hidden heap promotion — all rejected. Memory
movement must be visible.

DYNAMIC DISPATCH BY DEFAULT — Rejected. Trait calls use static
dispatch. Runtime dispatch requires explicit syntax if ever
introduced.

EXCEPTION HANDLING — Rejected in the traditional form. Hidden control
flow, unclear performance costs, and difficult deterministic cleanup.
Kru uses Result<T, E> and explicit return paths instead.

PREPROCESSOR — Rejected. Text substitution creates a second language
with separate rules. Compile-time features should operate on typed
program structures.

MANDATORY FRAMEWORKS — Rejected. The standard library provides
primitives, not application architecture. Kru does not prescribe web
frameworks, game engines, or application structures.

--------------------------------------------------------------------------------
Chapter 104 — Possible Standard Library Expansion
--------------------------------------------------------------------------------

Future standard modules may include:

    kru::compression     gzip, zstd, archive formats
    kru::image           image decoding and encoding
    kru::audio           low-level audio processing
    kru::gpu             graphics and compute interfaces
    kru::distributed     networking primitives

Each addition must satisfy: broad usefulness, predictable behavior,
zero unnecessary abstraction.

--------------------------------------------------------------------------------
Chapter 105 — Platform Expansion
--------------------------------------------------------------------------------

Kru intends to support multiple targets:

    x86_64
    ARM64
    RISC-V
    WebAssembly
    embedded microcontrollers

Each target must define: ABI, primitive sizes, alignment rules,
calling convention. Platform differences must be explicit:

    cfg(target = "arm")

rather than hidden compiler behavior.

--------------------------------------------------------------------------------
Chapter 106 — Community Proposals
--------------------------------------------------------------------------------

A proposal must include:

    Problem:      What issue does this solve?
    Design:       How does the feature work?
    Alternatives: Why were other approaches rejected?
    Costs:        Runtime cost, compile-time cost, complexity cost
    Compatibility: Does existing code change meaning?

A proposal without a clear problem statement is rejected.

--------------------------------------------------------------------------------
Chapter 107 — The Future Rule
--------------------------------------------------------------------------------

Kru is not designed to accumulate features forever. A smaller language
with strong guarantees is preferred over a larger language with
exceptions.

Every addition must preserve: simplicity, performance, determinism,
readability, explicit behavior.

The purpose of future development is not making Kru capable of
everything. The purpose is making Kru excellent at what it exists to
do: writing efficient, reliable systems software naturally.

APPENDIX A — FORMAL LANGUAGE GRAMMAR
================================================================================

This appendix defines the normative grammar of Kru 0.1 Alpha.

The grammar describes accepted source structure after lexical
processing. Whitespace and comments are removed before parsing except
where they affect token separation.

The grammar uses EBNF notation:

    {}      zero or more repetitions
    []      optional element
    |       alternative
    ()      grouping

The grammar is descriptive. Compiler implementations may use different
internal parser structures as long as accepted programs and diagnostics
remain consistent with this specification.

--------------------------------------------------------------------------------
A.1 Translation Units
--------------------------------------------------------------------------------

    translation_unit = { declaration }

    declaration =
          function_decl
        | struct_decl
        | enum_decl
        | trait_decl
        | impl_decl
        | const_decl
        | use_decl
        | type_decl
        | test_decl

    -- All declarations may be prefixed with ["pub"] to make them
    -- visible outside their module (Chapter 87).

--------------------------------------------------------------------------------
A.2 Functions
--------------------------------------------------------------------------------

    function_decl =
        ["pub"] ["extern" string_literal] ["inline" | "comptime"] "fn"
        identifier [generic_params]
        "(" [parameters] ")"
        ["->" type]
        block

    generic_params = "<" type_param { "," type_param } ">"

    type_param = identifier [":" type_bound { "+" type_bound }]

    parameters = param { "," param }

    param = ["ref" | "mut ref"] identifier ":" type
           | "self"                          // method receiver
           | "ref self"                       // by immutable reference
           | "mut ref self"                   // by mutable reference

--------------------------------------------------------------------------------
A.3 Variables
--------------------------------------------------------------------------------

    immutable_binding = "let" identifier [":" type] ":=" expression

    mutable_binding = "var" identifier [":" type] ":=" expression
                    | "var" identifier ":" type               // uninitialized

    assignment = lvalue "=" expression
               | lvalue compound_op expression

    compound_op = "+=" | "-=" | "*=" | "/=" | "%="
               | "&=" | "|=" | "^=" | "<<=" | ">>="

--------------------------------------------------------------------------------
A.4 Types
--------------------------------------------------------------------------------

    type =
          primitive_type
        | identifier
        | generic_type
        | ref_type
        | array_type
        | pointer_type
        | fn_type

    primitive_type =
        "i8" | "i16" | "i32" | "i64" | "i128"
        | "u8" | "u16" | "u32" | "u64" | "u128"
        | "isize" | "usize"
        | "f32" | "f64"
        | "bool" | "char" | "str"

    generic_type = identifier "<" type_list ">"

    ref_type = ["mut"] "ref" type

    array_type = "[" type ";" expression "]"

    pointer_type = "*" type           // naming the type is always
                                       // legal; constructing or
                                       // dereferencing a value of
                                       // this type is unsafe-only
                                       // (Chapter 26, "Raw Pointers")

    fn_type = "fn" "(" [type_list] ")" ["->" type]

--------------------------------------------------------------------------------
A.5 Expressions
--------------------------------------------------------------------------------

    expression =
          literal
        | identifier
        | path_expr
        | call_expr
        | field_expr
        | index_expr
        | slice_expr
        | binary_expr
        | unary_expr
        | match_expr
        | struct_expr
        | closure_expr
        | ref_expr
        | deref_expr
        | cast_expr
        | prop_expr
        | block_expr

    -- path_expr is for LEADING identifier chains only -- it never
    -- takes an arbitrary `expression` on its left, only another
    -- identifier or `::`. This is what separates it from field_expr
    -- below, which is defined recursively over `expression` and is
    -- what a normal `.method()` call actually parses through:
    --   Opcode.Jump(0x1000)   -- enum variant with payload
    --   Opcode.Store          -- enum variant without payload
    --   network::http::listen  -- fully qualified module path
    path_expr = identifier { ("::" | ".") identifier } ["(" [args] ")"]

    -- DISAMBIGUATION (path_expr vs. field_expr + call_expr):
    -- Both productions can match text like `a.b(c)`, but they are
    -- reached differently and the parser MUST prefer path_expr only
    -- at the point it is still consuming a leading identifier chain
    -- with no other expression already parsed. Concretely:
    --   1. Parsing begins at an identifier. Keep consuming `.name`
    --      or `::name` segments as path_expr for as long as each
    --      resolved segment names an enum type, a variant, or a
    --      module -- this is a name-resolution question, not a
    --      syntax one, so it is checked incrementally during parsing
    --      against the symbol table built so far (Chapter 44), not
    --      deferred to a later pass.
    --   2. The moment a segment does NOT resolve to one of those
    --      (e.g. it resolves to a local variable, a field, or is a
    --      method name), path_expr stops and everything parsed so
    --      far becomes the base `expression` for field_expr/
    --      call_expr instead. All subsequent `.name` segments are
    --      field_expr, and a following `(args)` wraps that field_expr
    --      in call_expr.
    -- Worked example: `data.len()` -- `data` does not resolve to an
    -- enum or module, so path_expr never applies; this parses as
    -- call_expr { callee: field_expr { data, len }, args: [] }.
    -- Worked example: `Opcode.Jump(0x1000)` -- `Opcode` resolves to
    -- an enum type and `Jump` to one of its variants, so this is a
    -- single path_expr all the way through, not a call_expr wrapping
    -- a field_expr.
    -- `::` segments are ALWAYS path_expr (module paths are never
    -- reached through field_expr); only `.` segments are ambiguous
    -- and require the rule above.

    -- During semantic analysis, the compiler confirms whether a
    -- path_expr refers to an enum variant or a module member. Enum
    -- variants with payloads are variant constructors; without
    -- payloads they are variant values.

    literal = INT_LIT | FLOAT_LIT | STR_LIT | CHAR_LIT | BOOL_LIT

    -- Generic type arguments, when present, come BEFORE the
    -- parenthesized argument list -- this matches every worked
    -- example elsewhere in this Codex (`identity<f64>(5)`,
    -- `cast<u16>(...)`), not after it.
    --
    -- DISAMBIGUATION (`<` `>` vs. less-than/greater-than): `<T>` is
    -- only ever parsed as generic_args when the token immediately
    -- preceding `<` is a callee that has already resolved (Chapter
    -- 44 name resolution, checked incrementally during parsing, same
    -- as the path_expr rule above) to a generic function, a generic
    -- type's constructor, or `cast`/`size_of`/`align_of`. In every
    -- other position `<` and `>` are the comparison operators from
    -- A.6, with their normal binary_expr precedence. This means a
    -- bare, unresolved identifier can never open a generic_args list
    -- -- `foo<a>(b)` where `foo` is not a known generic name parses
    -- as `(foo < a) > (b)`, a chained comparison, exactly as it would
    -- without generics in the language at all. Kru does not use a
    -- turbofish or other explicit marker; the resolved-name check is
    -- the entire disambiguation rule, and it is why every generic
    -- callee in this Codex is declared (`fn identity<T>(...)`) before
    -- any call site uses `<...>` against it.
    call_expr = expression ["<" type_list ">"] "(" [args] ")"

    field_expr = expression "." identifier

    index_expr = expression "[" expression "]"

    slice_expr = expression "[" range "]"

    range = [expression] ".." [expression]

    binary_expr = expression operator expression

    unary_expr = ("!" | "-" | "~") expression

    ref_expr = ["mut"] "ref" expression

    deref_expr = expression "@"

    cast_expr = "cast" "<" type ">" "(" expression ")"

    prop_expr = expression "?"

    block_expr = "{" { statement } [expression] "}"

    -- The optional trailing expression (not a statement) is the
    -- block's value. If omitted, the block's value is void.
    -- `ret` inside a block always returns from the enclosing
    -- FUNCTION, never from the block (Chapter 14).

    closure_expr = "fn" "(" [parameters] ")"
                   ["->" type] [capture_list] block

    capture_list = "[" capture { "," capture } "]"

    capture = ["mut"] ["ref"] identifier

--------------------------------------------------------------------------------
A.6 Control Flow
--------------------------------------------------------------------------------

    if_expr = "if" expression block ["else" (if_expr | block)]

    while_expr = [label ":"] "while" expression block

    for_expr = [label ":"] "for" ["ref" | "mut ref"] identifier "in"
              expression block

    -- The for loop iterates over the expression (array, slice,
    -- range, or any Iterable type). The loop variable may be
    -- prefixed with `ref` or `mut ref` to iterate by reference.

    loop_expr = [label ":"] "loop" block

    break_expr = "break" [label]

    continue_expr = "continue" [label]

    label = identifier

--------------------------------------------------------------------------------
A.7 Match
--------------------------------------------------------------------------------

    match_expr = "match" expression "{" { match_arm } "}"

    match_arm = pattern ["if" expression] "=>" block

    -- The optional `if expression` is a match guard (Chapter 15).
    -- Guards are evaluated after the pattern matches. A failing
    -- guard falls through to the next arm. Guards must be pure
    -- expressions (no side effects).

    pattern =
          literal
        | identifier ["(" [pattern_list] ")"]       // enum variant
        | identifier "{" { field_pattern } "}"         // struct destructuring
        | identifier "@" pattern                        // binding
        | "_"                                            // wildcard
        | pattern "|" pattern                            // alternation

    field_pattern = identifier [":" pattern] | ".."

--------------------------------------------------------------------------------
A.8 Structs & Enums
--------------------------------------------------------------------------------

    struct_decl = ["pub"] ["secure" | "component"] "struct"
                  identifier
                  ["(" type_list ")"]         // tuple struct
                  "{" { field } "}"
              | ["pub"] ["secure"] "struct" identifier    // unit struct

    -- `component` is only valid in .krux files (Chapter 70)
    -- `secure` enables memory wiping (Chapter 61)

    field = identifier ":" type [":=" expression]   // with default

    enum_decl = ["pub"] "enum" identifier [":" integer_type]
                "{" { variant } "}"

    variant = identifier ["(" params ")] ["=" expression]

    struct_expr = identifier "{" { field_init } "}"

    field_init = identifier ":" expression

--------------------------------------------------------------------------------
A.9 Declarations
--------------------------------------------------------------------------------

    const_decl = ["pub"] "const" identifier [":" type] ":=" expression

    type_decl = ["pub"] "type" identifier ":=" type

    use_decl = "use" module_path
             | "use" string_literal           // .kh header import

    module_path = identifier { "::" identifier }

--------------------------------------------------------------------------------
A.10 Statements
--------------------------------------------------------------------------------

    statement =
          declaration
        | immutable_binding
        | mutable_binding
        | assignment
        | expression
        | if_expr
        | while_expr
        | for_expr
        | loop_expr
        | break_expr
        | continue_expr
        | "ret" [expression]
        | "unsafe" block
        | "arena" identifier block
        | "comptime" block
        | "test" string_literal block

    test_decl = "test" string_literal block

END OF APPENDIX A — FORMAL LANGUAGE GRAMMAR

================================================================================
APPENDIX B — TYPE SYSTEM REFERENCE
================================================================================

The Kru type system is static, explicit where ambiguity exists, and
resolved completely before native code generation.

No runtime type metadata exists unless explicitly created by a future
reflection system.

--------------------------------------------------------------------------------
B.1 Type Identity
--------------------------------------------------------------------------------

Two types are identical only when:
  - they have the same primitive identity
  - they reference the same declared type
  - their generic parameters match exactly

    List<i32> and List<u32> are different types.

--------------------------------------------------------------------------------
B.2 Inference Rules
--------------------------------------------------------------------------------

Kru allows local inference:

    let size := 128         // compiler infers i32
    let big := 2_000_000_000 // compiler infers i64 (exceeds i32 range)

Inference does not cross function boundaries. Public APIs should
explicitly declare parameter and return types.

    Preferred:  pub fn connect(port: u16) -> Connection
    Avoid:      pub fn connect(port) -> ???

--------------------------------------------------------------------------------
B.3 Numeric Conversion
--------------------------------------------------------------------------------

Numeric conversions are explicit. Implicit narrowing is forbidden.

    let value: u8 := 500      // error: literal exceeds u8 range

Explicit conversion:

    let value := cast<u8>(500)
    let port := cast<u16>(8080)

The `cast<T>()` built-in performs a checked conversion. Conversions
that lose data (e.g. f64 to i32 with a fractional component) truncate
silently — the programmer asked for it explicitly. Conversions that
exceed the destination range produce a compile error for literals,
or a runtime panic for computed values.

--------------------------------------------------------------------------------
B.4 Generic Type Identity
--------------------------------------------------------------------------------

Generic types are compile-time templates. The compiler does not store
`Vector<T>` at runtime. Instead it generates:

    Vector__i32
    Vector__f32
    Vector__Packet

for each required specialization.

END OF APPENDIX B — TYPE SYSTEM REFERENCE

APPENDIX C — APPLICATION BINARY INTERFACE
================================================================================

The Kru ABI defines the rules required for interoperability between
compiled Kru modules, Kru-X applications, generated `.kh` interfaces,
and external native interfaces.

The ABI exists to provide predictable communication between separately
compiled units.

The ABI is target-specific where required. A Windows x64 binary and a
Linux x64 binary may use different machine conventions while still
conforming to the same Kru ABI rules.

--------------------------------------------------------------------------------
C.1 ABI Guarantees
--------------------------------------------------------------------------------

A conforming Kru ABI provides:
  - deterministic symbol generation
  - deterministic type layout
  - compatible calling conventions
  - stable public interfaces
  - no hidden runtime dependencies

The ABI does not provide:
  - garbage collector integration
  - object metadata
  - implicit allocation
  - runtime reflection information

--------------------------------------------------------------------------------
C.2 Calling Convention
--------------------------------------------------------------------------------

The default Kru calling convention is `kru`. The compiler lowers this
convention into the platform-native ABI:

    x86_64 System V (Linux, macOS)
    x86_64 Windows ABI
    ARM64 Procedure Call Standard

A Kru function:

    pub fn add(a: i32, b: i32) -> i32

is represented as a native function:

    i32 add(i32, i32)

No hidden context pointer is passed. No implicit object receiver
exists unless defined by method syntax.

EXTERNAL C ABI
    Functions marked `extern "C"` use the platform's C calling
    convention for FFI interoperability:

    extern "C" fn memcmp(a: *u8, b: *u8, n: usize) -> i32

    Such functions can only be called inside `unsafe` blocks.

--------------------------------------------------------------------------------
C.3 Symbol Naming
--------------------------------------------------------------------------------

Public symbols use their fully-qualified module path:

    network::server::listen

Internal representation:

    network__server__listen

Generic instantiations append concrete types:

    identity<i32>  becomes  identity__i32

Multiple generic parameters:

    map<Result<i32, Error>, String>
    becomes  map__Result_i32_Error__String

Name mangling must be deterministic.

--------------------------------------------------------------------------------
C.4 Struct ABI Layout
--------------------------------------------------------------------------------

Struct layout follows declaration order. The compiler may insert
required alignment padding. The compiler may not reorder fields
unless an explicit layout attribute permits it.

    struct Header {
        magic: u32       // offset 0
        version: u16     // offset 4
        flags: u16       // offset 6
    }

    #[layout(packed)]     // no padding
    #[layout(align(16))] // 16-byte aligned

--------------------------------------------------------------------------------
C.5 External Interfaces
--------------------------------------------------------------------------------

`.kh` files describe ABI-visible declarations:

    pub fn initialize() -> bool

A `.kh` file contains: public functions, public structs, public
enums, constants, and ABI attributes. Private implementation details
are excluded.

APPENDIX E — DIAGNOSTIC FORMAT
================================================================================

Diagnostics are part of the Kru language experience.

A compiler diagnostic must answer: What happened? Why? How to fix?

--------------------------------------------------------------------------------
E.1 Diagnostic Structure
--------------------------------------------------------------------------------

    level[code]: summary

    source location

    explanation

    suggested fix

Example:

    error[K1004]: cannot modify immutable binding

      5 | let value := 10
      6 | value = 20
             ^ immutable binding

    Why:
        `value` was declared using `let`.

    Fix:
        var value := 10

--------------------------------------------------------------------------------
E.2 Diagnostic Levels
--------------------------------------------------------------------------------

    error     Compilation cannot continue.
    warning   Code is valid but suspicious.
    note      Additional context (cannot exist alone).
    help      Suggested correction with optional machine-fix.

--------------------------------------------------------------------------------

--------------------------------------------------------------------------------

    K1xxx        Language errors
      K1001-K1099  Name resolution
      K1100-K1199  Type checking
      K1200-K1299  Parser
      K1300-K1399  Trait/generic resolution
    K2xxx        Warnings
      K2000-K2099  Correctness
      K2100-K2199  Style
      K2200-K2299  Performance
      K2300-K2399  Security
      K2400-K2499  Compatibility
    K3xxx        Memory system errors
    K4xxx        Security errors
    K5xxx        Compiler/toolchain errors

Error codes remain stable across compiler releases.

APPENDIX F — MEMORY MODEL DIAGRAMS

--------------------------------------------------------------------------------
F.1 Stack Memory
--------------------------------------------------------------------------------

    fn process() {
        let value := 10
    }

    STACK FRAME
    +----------------+
    | value: i32     |
    +----------------+

    Scope exit: value destroyed

--------------------------------------------------------------------------------
F.2 Arena Memory
--------------------------------------------------------------------------------

    arena scratch {
    +----------------+
    | object A       |
    | object B       |
    | object C       |
    | free space     |
    +----------------+
    }

    Arena exit: entire block released.
    Individual objects do not require manual destruction.

--------------------------------------------------------------------------------
F.3 Reference Rules
--------------------------------------------------------------------------------

    Immutable sharing:
             value
          /    |    \
        ref   ref   ref        Allowed.

    Mutable access:
             value
              |
             ref                  Allowed (exactly one mut ref).

    Mixed:
             value
          /         \
       ref       mut ref          Forbidden outside unsafe.

--------------------------------------------------------------------------------
F.4 Move Semantics
--------------------------------------------------------------------------------

    let a := String.from("hi")
    let b := a                     // a MOVED to b

    BEFORE:           AFTER:
    +-------+         +-------+
    | a     |         | a     | (invalid)
    | ptr---+         | ?----? |
    +-------+         +-------+
                      +-------+
                      | b     |
                      | ptr---+---> "hi"
                      +-------+

--------------------------------------------------------------------------------
F.5 Copy Semantics (Copy trait)
--------------------------------------------------------------------------------

    let x := 5
    let y := x                     // x COPIED to y (i32 is Copy)

    BEFORE:           AFTER:
    +-------+         +-------+
    | x: 5  |         | x: 5  | (still valid)
    +-------+         +-------+
                      +-------+
                      | y: 5  |
                      +-------+

APPENDIX H — DESIGN PRINCIPLES SUMMARY
================================================================================

--------------------------------------------------------------------------------
H.1 Simplicity
--------------------------------------------------------------------------------

A feature should reduce programmer effort without hiding machine
behavior.

--------------------------------------------------------------------------------
H.2 Predictability
--------------------------------------------------------------------------------

The programmer should be able to determine: where data exists, when
data is destroyed, what code executes, what the compiler generates.

--------------------------------------------------------------------------------
H.3 Performance
--------------------------------------------------------------------------------

The default path should produce efficient native code. Performance-
critical behavior should not require abandoning normal Kru.

--------------------------------------------------------------------------------
H.4 Safety
--------------------------------------------------------------------------------

Safe Kru code should prevent common memory failures. Unsafe behavior
must be explicit.

--------------------------------------------------------------------------------
H.5 Final Evaluation Rule
--------------------------------------------------------------------------------

Every future proposal must answer:

    "Does this make efficient systems programming simpler without
     hiding how the machine works?"

    If yes: the feature may belong in Kru.
    If no:  the feature does not belong in Kru.

APPENDIX I — IMPLEMENTATION ORDER FOR LINUX/KATE
================================================================================

This appendix provides a recommended implementation order for the
bootstrap compiler, optimized for development on Linux using the
Kate text editor. Each phase builds on the previous one and produces
a testable artifact.

The reference bootstrap compiler is implemented in plain C and should
remain self-contained: no LLVM, libclang, parser generator, or external
compiler framework is required. A bootstrap implementation in another host
language is permitted by the language specification, but the canonical
backend contract in Chapter 47 remains direct native emission.

--------------------------------------------------------------------------------
Phase 1: Lexer (Chapter 41)
--------------------------------------------------------------------------------

    Goal: text -> token stream
    Input: .kru source files
    Output: Vec<Token> with spans

    Implement: all token types from Chapter 5 (keywords, identifiers,
    integer/float/char/string literals with escape sequences,
    operators, punctuation, comments). Produce three-part error
    messages from the start — good diagnostics are easier to build in
    early than retrofit.

    Test: feed malformed source, verify error messages.

--------------------------------------------------------------------------------
Phase 2: Parser (Chapter 42)
--------------------------------------------------------------------------------

    Goal: token stream -> AST
    Input: Vec<Token>
    Output: AST with spans

    Implement: recursive descent for declarations, Pratt parser for
    expressions. All AST node types from Chapter 43. Error recovery
    at statement boundaries (Chapter 82).

    Test: parse all example programs from the Codex.

--------------------------------------------------------------------------------
Phase 3: AST Printer
--------------------------------------------------------------------------------

    Goal: pretty-print the AST for debugging

    This is not a compiler feature — it's a development tool. Being
    able to see the AST as text catches parser bugs fast. Keep this
    around for the rest of development.

--------------------------------------------------------------------------------
Phase 4: Semantic Analysis (Chapter 44)
--------------------------------------------------------------------------------

    Goal: annotated AST

    Implement in order:
      1. Name resolution (Chapter 44.1)
      2. Type checking and inference (Chapter 44.2)
      3. Move tracking (Chapter 44.3)
      4. Trait resolution (Chapter 44.4)
    Defer aliasing/lifetime checking to Phase 7.

    Test: type-check all example programs, verify error messages for
    type mismatches and unknown identifiers.

--------------------------------------------------------------------------------
Phase 5: HIR + Monomorphization (Chapter 45)
--------------------------------------------------------------------------------

    Goal: desugared, monomorphized HIR

    Implement: desugar ? to match, compound assignment to binary+
    assign, while to loop+if. Monomorphize generics. Deduplicate
    identical specializations.

--------------------------------------------------------------------------------
Phase 6: Minimal Direct Native Codegen (Chapter 47)
--------------------------------------------------------------------------------

    Goal: HIR/MIR -> x86-64 machine code -> ELF executable

    Implement the smallest direct emitter first: ELF64 headers, executable
    segments, integer constants/arithmetic, return/exit, then functions,
    calls, stack locals, branches, and loops. Add relocations and object-file
    emission as soon as multi-function/data-section code requires them.

    Linux target: x86_64 System V ABI. The compiler writes machine code and
    ELF/object structures itself; no external assembler, linker, or compiler
    framework is required for programs inside the supported subset.

    A C-output bootstrap/reference backend may remain available in parallel
    while the native backend grows.

    Test: compile and run a constant-return program directly from Kru, then
    expand the conformance cases one instruction family at a time.

--------------------------------------------------------------------------------
Phase 7: MIR + Memory Checks (Chapter 46)
--------------------------------------------------------------------------------

    Goal: control-flow graph with dataflow analysis

    Implement: MIR lowering, arena-liveness analysis, aliasing-XOR-
    mutability check, @ validity check. Mark unsafe regions where
    checks are skipped.

    Test: compile programs that should fail memory checks, verify
    error messages reference the correct source location.

--------------------------------------------------------------------------------
Phase 8: Comptime Interpreter (Chapter 49)
--------------------------------------------------------------------------------

    Goal: evaluate comptime blocks during compilation

    Implement: sandboxed bytecode interpreter, step limit,
    deterministic-only intrinsics.

--------------------------------------------------------------------------------
Phase 9: Standard Library (Volume VI)
--------------------------------------------------------------------------------

    Implement in order of dependency:
      1. kru::io (pr, stdout — needed for everything)
      2. kru::mem (Heap, arenas)
      3. kru::fs (file I/O)
      4. kru::str (string manipulation)
      5. kru::collections (Array, Vector, Map)
      6. kru::net (sockets, HTTP)
      7. kru::thread + kru::sync
      8. kru::crypto
      9. kru::db

--------------------------------------------------------------------------------
Phase 10: Tooling (Volume XI)
--------------------------------------------------------------------------------

    Implement in order:
      1. kru fmt (formatter)
      2. kru test (test runner)
      3. kru build (build system)
      4. kru lsp (language server)
      5. kru dbg (debugger)
      6. kru doc (documentation generator)

    Kate integration: configure kru lsp as the language server for
    .kru files in Kate's settings. Kate supports LSP via the
    LSP Client plugin.

--------------------------------------------------------------------------------
Development Notes
--------------------------------------------------------------------------------

    - Build incrementally: get Phase 1-6 working before attempting
      memory analysis or comptime.
    - Write test programs in Kru alongside the compiler. Each example
      in this Codex should compile and run once the relevant phase
      is complete.
    - Keep diagnostic quality high from the start. Retrofitting good
      error messages is painful.
    - Use Kate's built-in terminal (F7) for quick compile-test
      cycles. Configure a build target for `kru build` in Kate's
      project settings.
    - Keep native backend tests architecture-specific and explicit. A target
      backend that does not implement a construct must reject it rather than
      falling through to incorrect machine code.

J.8 Second Revision — Spec Review Fixes
--------------------------------------------------------------------------------

  The following changes were made after a full spec review identified
  8 consistency bugs and several design gaps. Each fix is documented
  for traceability.

  45. REMOVED `mod` FROM KEYWORDS. Chapter 6 still listed `mod` as a
      reserved keyword despite Appendix J (first revision) item 30
      claiming it was removed. Now actually removed — modules are
      filename-based (Chapter 87).

  46. ADDED `extern`, `for`, `in` TO KEYWORDS. `extern` is needed for
      FFI declarations (Appendix C). `for` and `in` are needed for the
      new for-loop feature (item 52). Moved from reserved-for-future
      to active keywords.

  47. REMOVED `as` OPERATOR — UNIFIED ON `cast<T>()`. Chapter 17 used
      `as` for enum discriminant conversion (`HttpStatus.Ok as u16`)
      but `as` was never in the keyword list, operator list, or grammar.
      Replaced with `cast<u16>(HttpStatus.Ok)`, matching the existing
      `cast<T>()` syntax used for numeric conversions (Appendix B.3).
      Kru now has exactly one cast mechanism.

  48. ADDED `extern` TO GRAMMAR. Appendix C.2 showed `extern "C" fn`
      but the formal grammar (A.2) had no `extern` production. Added
      `["extern" string_literal]` to function_decl.

  49. ADDED `pub` TO ALL DECLARATION GRAMMAR. The grammar only allowed
      `pub` on functions. Added `["pub"]` to struct_decl, enum_decl,
      const_decl, and type_decl in Appendix A. Added `test_decl` as
      a standalone declaration production.

  50. FIXED `secure` STRING LITERAL SYNTAX. Chapter 63 used `secure
      "string"` prefix syntax that had no grammar production and
      conflicted with `secure` being a struct modifier. Replaced with
      `SecureString.from_encrypted("string")`, which is a standard
      library function call consistent with Chapter 62's
      `SecureString.from()`.

  51. FIXED STRING CONCATENATION EXAMPLE. Chapter 20 showed
      `String.from(first).push_str(last)` which returns void (push_str
      modifies in place), not a concatenated String. Fixed with two
      correct patterns: in-place modification and a `concat()` function.

  52. ADDED `for` LOOP. Chapter 19 previously required manual index
      iteration (`while i < data.len()`) for all collection traversal.
      Added `for item in collection { }` syntax with: by-value and
      by-reference iteration, range-based index iteration, labeled
      break/continue, and Iterable trait desugaring. Added `for_expr`
      to the grammar (A.6). Moved `for`/`in` from reserved to active
      keywords. Updated Volume XII to reflect for-loop is now in 0.1.

  53. ADDED MATCH GUARDS. Chapter 15 previously reserved match guards
      (`if condition` on match arms) for a future revision. Made them
      active in 0.1 Alpha with: guard semantics (fall-through on
      failure), pattern binding access, purity requirement (K1006:
      impure expression in match guard), and always-false guard
      warning (K2003). The grammar (A.7) already had the `if` guard
      production — now it's documented as active.

  54. FIXED EXPRESSION BLOCK `ret` SEMANTICS. Chapter 14 overloaded
      `ret` to mean "return from block" inside expression blocks and
      "return from function" everywhere else. Changed to last-expression
      semantics: a block's value is its last expression (no `ret`
      needed), and `ret` always returns from the enclosing function.
      Updated grammar (A.5) block_expr with a comment documenting
      this rule.

  55. CLARIFIED `@` OPERATOR WITH METHOD CALLS. Chapter 10 did not
      specify how `@` interacts with method calls (`ptr@.method()`).
      Added explicit precedence documentation: `@` binds first
      (level 1), so `ptr@.method()` loads the value then calls the
      method on the loaded value. To call through a reference without
      loading, use `ptr.method()` with `ref self`/`mut ref self` receiver.

  56. CLARIFIED CLOSURE ESCAPE RULES. Chapter 13 mentioned closures
      that escape requiring "an explicit `arena` or heap annotation"
      but never defined what triggers the requirement or what the
      annotation looks like. Replaced with precise rules: by-value
      captures may escape freely; by-reference captures that escape are
      a compile error (K3003). Documented three workarounds.

  57. SPECIFIED KRU-X COMPONENT MODEL. Chapter 70 described
      component-scoped arenas but never specified what makes a struct
      a "component." Added the `component` keyword (Kru-X contextual
      keyword, valid only in .krux files) with full semantics:
      lifecycle (mount/unmount), state persistence, render method
      requirement, and nesting rules. Added `component` to struct_decl
      in the grammar (A.8). Non-component structs in .krux files
      behave exactly as in Kru.

  58. ADDED `path_expr` TO GRAMMAR. Enum variant construction
      (`Opcode.Jump(0x1000)`) and module paths (`network::http::listen`)
      had no grammar production. Added `path_expr` to handle both,
      with semantic analysis resolving whether a path is an enum
      variant, module member, or field access.

  59. ADDED NEW DIAGNOSTIC CODES. K1006 (impure expression in match
      guard), K2002 (missing documentation), K2003 (match arm with
      always-false guard), K3003 (escaping closure captures reference
      to local binding). All added to the error code list (Chapter 79)
      with appropriate categories.

  60. UPDATED ITERABLE TRAIT. Changed from "(future)" to active in
      Chapter 32, with documentation that it provides `.iter()`/`.next()`
      for the for-loop desugaring (Chapter 19).

J.9 Third Revision — Implementation-Driven Fixes
--------------------------------------------------------------------------------

  The following changes were made after the bootstrap compiler (kru0)
  and its test fixtures exposed gaps the previous two reviews missed —
  each is a place where either the Codex contradicted its own worked
  examples, or a real fixture (`tests/stage5.kru` et al.) had already
  made an implementation choice the Codex never actually sanctioned.

  61. FIXED `call_expr` GRAMMAR ORDERING. Appendix A.5 defined
      `call_expr = expression "(" [args] ")" ["<" type_list ">"]` —
      generic arguments AFTER the parenthesized args. Every worked
      example in the Codex (`identity<f64>(5)`, `cast<u16>(...)`)
      places them BEFORE. Fixed to
      `call_expr = expression ["<" type_list ">"] "(" [args] ")"`.

  62. DOCUMENTED THE `<T>` DISAMBIGUATION RULE. Item 58 (second
      revision) added `path_expr` but the `<`/`>` generic-call
      ambiguity with the comparison operators was never addressed
      anywhere. Added an explicit rule to A.5: `<T>` is only parsed
      as generic_args when the callee has already resolved, during
      parsing, to a known generic name; otherwise `<`/`>` are the
      comparison operators. No turbofish or other marker — the
      resolved-name check is the whole rule.

  63. DOCUMENTED THE `path_expr` VS. `field_expr`+`call_expr`
      PRECEDENCE RULE. Item 58 added the `path_expr` production but
      did not say which production wins when both can match the same
      text (`a.b(c)`). Added an explicit incremental-resolution rule
      to A.5: path_expr only continues consuming `.name` segments
      while each one resolves to an enum type/variant or a module;
      the moment a segment doesn't, parsing falls through to
      field_expr/call_expr instead. `::` segments are always
      path_expr. Worked examples for both cases added inline.

  64. DEFINED RAW POINTERS (`*T`) AS A DISTINCT CONCEPT FROM `ref T`.
      Chapter 26 covered `ref`/arena-derived pointer validity in
      detail but never actually defined what a raw pointer is, how
      it's obtained, or how its `unsafe` requirement differs from
      `ref T`'s "provable outside unsafe" escape hatch. Added a "RAW
      POINTERS" section to Chapter 26: naming `*T` as a type needs no
      `unsafe`; constructing or dereferencing one always does, because
      Chapters 24-25's liveness proof never applies to raw pointers.
      Chapter 27's permitted-operations list now names this
      explicitly instead of leaving it implicit in "raw pointer
      arithmetic."

  65. ADDED `null` AS A SCOPED BUILT-IN. `null` was used by
      `tests/stage5.kru` and was never defined anywhere in the Codex
      — absent from both the keyword list and built-in identifiers
      (Chapter 6), despite `Option`/`None` covering "no value"
      everywhere else. Added `null` to Chapter 6's built-ins and to
      the new Chapter 26 "RAW POINTERS" section, scoped narrowly: only
      valid where a `*T` type is expected, does not participate in
      `match`, and does not generalize beyond raw pointers — `Option`
      remains the idiomatic choice at ordinary API boundaries.

  66. SPECIFIED WHOLE-ARRAY-TO-SLICE DECAY. Chapter 19 only ever
      constructed a `ref [T]` slice via range syntax (`data[1..4]`);
      `ref arr` on a whole `[T; N]` with no range was used in
      `tests/stage5_arrays.kru` but never specified. Added a
      "WHOLE-ARRAY DECAY" note to Chapter 19: `ref arr` is exactly
      `ref arr[..]` — Kru has no separate "reference to a fixed-size
      array" type; every array reference is a slice.

  None of items 61-66 are yet enforced by kru0 — the compiler has not
  caught up to these clarifications (in particular, `unsafe` is not
  yet a required or even parsed construct in the bootstrap compiler,
  so item 64's `unsafe`-only rule for raw pointers is not currently
  checked). Per this Codex's own precedence statement (page 1): the
  specification leads, the compiler follows.
